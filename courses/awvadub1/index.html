WSL2Ubantu网络加速

约 3196 字大约 11 分钟

2026-11-04

针对你所在的Ubuntu WSL环境，想流畅访问GitHub和Kaggle，可以从“全局工具”、“镜像替换”和“临时配置”几个层面入手。下面整理了不同场景下的方案，你可以按需选择。

🚀 一站式加速工具（推荐，省心高效）

这类工具可以同时解决GitHub、Docker、Python包等多个源的加速问题，适合希望一劳永逸的场景。

  • Xget：一个基于Cloudflare的开源加速引擎，能加速GitHub、Kaggle、Docker、PyPI等众多平台。

    • 加速Git Clone：git clone https://xget.xi-xu.me/gh/microsoft/vscode.git
    • 加速Docker Pull：docker pull xget.xi-xu.me/cr/ghcr/nginxinc/nginx-unprivileged:latest
    • 加速Pip：pip config set global.index-url https://xget.xi-xu.me/pypi/simple/

  • CNFast：另一个专为国内开发者设计的工具，支持GitHub和Docker Hub等加速。

    • 安装：curl -fsSL https://gitee.com/sallai/cnfast/raw/main/install.sh | bash
    • 使用：cnfast git clone https://github.com/microsoft/vscode.git

🛠️ 专用代理与工具箱

这类工具通过在本地运行代理服务，为特定应用提供加速。

  • FastGithub：专门解决GitHub访问问题的神器，支持Linux终端。

    • 下载与运行：从GitHub Releases下载Linux版本，然后运行 sudo ./fastgithub。
    • 配置：运行后，需设置系统或Git的HTTP/HTTPS代理为 http://127.0.0.1:38457。

  • Watt Toolkit (原Steam++)：跨平台工具箱，内置GitHub加速功能。在官网下载安装后，在插件列表中找到GitHub并开启加速即可。

  • DevSidecar：同样是一款轻量级代理客户端，可以为GitHub全协议提供统一加速通道。

🌐 反向代理与镜像（最快捷，无需安装）

如果只是临时需要clone某个仓库或下载文件，直接在URL前添加代理前缀是最快的方法。

  • 通用代理前缀：https://githubproxy.cc/ 或 https://ghfast.top/。

    • 加速Clone：git clone https://githubproxy.cc/kubernetes/kubernetes.git
    • 加速下载Release文件：在原始链接前加上代理前缀即可。

  • 针对Kaggle的加速：Xget等一站式工具明确支持Kaggle，可以使用类似 https://xget.xi-xu.me/kg/... 的地址进行加速。

📝 手动配置（作为备用或补充）

  • 修改Hosts文件：手动将GitHub相关域名指向最优IP，可以解决DNS污染问题。

    • 操作：编辑 /etc/hosts 文件（需sudo权限），将 https://github.com/521xueweihan/GitHub520 提供的最新IP地址粘贴进去。
    • 刷新DNS缓存：sudo systemd-resolve --flush-caches。

  • 为Git设置代理：如果你本地已经有代理服务（如Clash），可以只让Git走代理。

    • 设置：git config --global http.https://github.com.proxy socks5://127.0.0.1:1080（请将端口号替换为你实际的代理端口）。
    • 取消：git config --global --unset http.https://github.com.proxy。

💡 针对Kaggle的补充建议

  • 使用Kaggle API：通过官方命令行工具 kaggle 下载数据集，通常比网页下载更稳定，且支持断点续传。
  • 多线程下载工具：对于Kaggle上的大文件，可以使用 aria2 等多线程下载工具来加速。

你可以根据使用频率和习惯来选择。如果希望一劳永逸，推荐优先尝试 Xget 或 FastGithub。如果只是偶尔使用，反向代理前缀是最轻量的选择。

Xget 的设计思路是“URL替换”，而不是传统的代理软件，所以它不需要复杂的安装过程，直接通过修改各工具的配置或命令来使用即可。针对你 WSL2 下的 Ubuntu 环境，核心的 Git、Conda、Pip 和 Docker 配置方法如下。

🚀 核心原理：URL 替换

Xget 的核心是一个统一的加速域名 xget.xi-xu.me，你只需要在原地址前加上对应的平台前缀即可。

例如，加速 GitHub 的地址：

  • 原始：https://github.com/microsoft/vscode
  • 加速：https://xget.xi-xu.me/gh/microsoft/vscode

常用的平台前缀有：gh (GitHub)、pypi (PyPI)、conda (Conda)、cr (容器镜像) 等。

🛠️ 针对你环境的详细配置

1. Git 全局加速（一劳永逸）

这是最推荐的配置，执行一次后，所有 git clone 都会自动走加速通道。

在 Ubuntu 终端中执行：

git config --global url."https://xget.xi-xu.me/gh/".insteadOf "https://github.com/"

注意：这个配置会全局替换所有 GitHub 的 Git 操作。如果你后续配置了 SSH Key，git@github.com 的 SSH 协议不受影响，可以放心使用。

2. Pip (Python包) 加速

设置全局镜像源即可：

pip config set global.index-url https://xget.xi-xu.me/pypi/simple/
pip config set global.trusted-host xget.xi-xu.me

验证配置：pip config list。

3. Conda 环境加速

由于你使用 Miniconda，配置 Conda 的 channel 镜像会极大提升创建环境的速度。推荐直接配置 channel_alias，这样所有社区源都会自动加速：

conda config --set channel_alias https://xget.xi-xu.me/conda/community

如果需要配置官方源，可以追加：

conda config --add default_channels https://xget.xi-xu.me/conda/pkgs/main
conda config --add default_channels https://xget.xi-xu.me/conda/pkgs/r
conda config --add default_channels https://xget.xi-xu.me/conda/pkgs/msys2

验证配置：conda config --show。

4. Docker 镜像加速

注意：Docker 的配置需要修改守护进程文件 /etc/docker/daemon.json，必须使用 sudo。

  1. 使用 sudo nano /etc/docker/daemon.json 编辑配置文件。
  2. 添加或修改 registry-mirrors 字段，指向 Xget 的容器镜像前缀：
    {
  "registry-mirrors": ["https://xget.xi-xu.me/cr"]
}
  3. 保存后，重启 Docker 服务使配置生效：
    sudo systemctl restart docker

提示：使用镜像加速后，docker pull 命令仍然保持原样（例如 docker pull nginx），Docker 会自动通过配置的镜像源拉取。如果你想直接指定 Xget 的完整地址，格式为 xget.xi-xu.me/cr/docker/nginx。

💡 补充说明与进阶

  • Kaggle 加速：Xget 的加速列表里包含了 Kaggle。你可以通过 URL 转换器 xuc.xi-xu.me，将 Kaggle 的数据集链接转换成 Xget 格式进行加速下载。
  • 公共实例的稳定性：xget.xi-xu.me 是官方提供的公共实例，适合评估和日常使用，但官方也提示，对于生产环境或对可用性要求极高的场景，建议自行部署。
  • 取消 Git 全局加速：如果未来你需要恢复默认配置，可以执行以下命令：
    git config --global --unset url."https://xget.xi-xu.me/gh/".insteadOf

针对你“WSL2 长期跑计算，需要稳定访问 GitHub 和 Kaggle”的场景，Xget 是一个很好的“起点”，但它并非“最适合”的终极方案。最适合你的应该是一套以官方工具为主，加速工具为辅的组合策略。

🎯 Xget 的适用性与局限

Xget 最大的优势是“轻量、无需部署”，修改一下 Git 或包的配置就能用。但它的一个关键局限在于稳定性。

官方明确说明，公共实例 xget.xi-xu.me “不保证可靠性”，仅适合评估与试用，对于生产环境或对可用性敏感的场景，建议自行部署。你的服务器是要长期跑计算任务的，如果依赖一个不保证可靠性的公共加速服务，一旦它出现波动或中断，可能会直接影响你的工作流。此外，它的加速效果也依赖于 Cloudflare 边缘节点的状况，在某些网络环境下可能并不理想。

📊 主流加速方案横向对比

为了帮你更清晰地做选择，这里将几种方案在你 WSL2 环境下的适用性做个对比：

方案核心原理在 WSL2 中的配置复杂度稳定性 / 可靠性最适合的场景
XgetURL 替换低（修改 Git/Pip/Conda 配置）中低（公共实例不保证）快速测试、临时加速、个人非关键任务
FastGithub本地代理 + 智能 DNS中（需下载运行，并配置 Git 代理）较高（专为 GitHub 优化，社区活跃）GitHub 重度用户，追求稳定访问
Watt Toolkit系统代理中高（需在 Windows 宿主机配置，WSL2 手动设代理）中（依赖宿主机代理稳定性）Windows 桌面端日常开发，同时想兼顾 WSL2
SSH 协议 (你已配置)走 443 端口低（已完成）高（原生协议，但需网络不封锁 443）所有 git clone/push/pull 操作
Kaggle API官方命令行工具低高（官方支持，支持断点续传）所有 Kaggle 数据集下载
镜像站 / 反向代理URL 前缀替换极低（无需配置）中（依赖镜像站稳定性）临时下载 Release 文件或 Clone 仓库

💎 给你的组合方案建议

综合来看，最适合你的不是一个单一工具，而是一个分层的策略：

  1. GitHub 操作（clone/push/pull）：继续使用你已经配好的 SSH (443端口) 方案。这是最稳定、最原生的方式，你之前的成功配置已经证明了它在你的网络环境下是通的。只有当 SSH 偶尔不稳定时，才考虑用 FastGithub 作为备用（在 WSL2 内直接运行，配置 Git 代理），它比 Xget 的公共实例更专注于 GitHub 的稳定性。

  2. Kaggle 数据集下载：放弃使用 Xget 或 Watt Toolkit 这类通用加速器，直接使用官方的 kaggle CLI 工具。这是最可靠的方式，支持断点续传，适合下载大文件。如果 CLI 速度仍不理想，再考虑为其配置代理（指向你 Windows 上运行的代理或 FastGithub 的本地端口）。

  3. Python / Conda 包管理：Xget 在这里是一个不错的选择。因为包管理器的重试机制相对完善，对单次连接的稳定性要求不如长时 Git 操作那么高。用 Xget 来加速 pip 和 conda 的下载，是“利大于弊”的便捷选择。

总结一下：Xget 可以作为你加速 Pip/Conda 的轻量工具，但在核心的 GitHub 操作和 Kaggle 数据下载上，已经配好的 SSH 和官方 Kaggle CLI 才是你更稳定、更可靠的主力方案。

完全可以，而且非常推荐！ 在跑生信分析或分子动力学模拟时，通常都需要“多窗口”配合（比如一个窗口跑计算，另一个窗口看资源占用，再开一个窗口改代码）。

在你这套“Windows -> Tailscale -> WSL2 Ubuntu”的架构下，你有以下几种开多窗口的姿势：

🥇 方法一：在 VS Code 里开“分屏”或“多标签”（最推荐）

既然你已经在用 VS Code 远程连接，这是最优雅的方式：

  1. 多开终端：在 VS Code 底部终端面板的右上角，点击 + 号，就可以新建无数个终端。它们都在同一个 Ubuntu 环境里，互不干扰。
  2. 分屏终端：点击终端面板右上角的分屏图标（两个方块拼在一起的图标），就可以把终端左右或上下切开，一边运行程序，一边看 htop 监控内存。
  3. VS Code 本身多窗口：你可以按 Ctrl+Shift+P，输入 Remote-SSH: Connect to Host...，再选一次你的服务器，VS Code 会弹出一个全新的独立窗口，连接到同一个 Ubuntu 服务器。

🥈 方法二：在远程 Windows 上开多个 PowerShell（独立窗口）

在你的远程 Windows 机器上，你可以打开多个 PowerShell 窗口，每个窗口都通过 SSH 连进去：

ssh aikemi@100.121.21.105

你可以开三个窗口：一个用于跑数据，一个用于测试脚本，一个用来监控。它们是完全独立的 SSH 会话。

💡 进阶大招：跑长任务必须懂的“后台运行”

千万要注意： 如果你只是开多个窗口跑计算，一旦你的远程 Windows 电脑断网、休眠，或者你不小心关掉了那个窗口，正在跑的 Ubuntu 计算任务就会立刻被强制终止（进程被杀掉）！

跑几天几夜的分子动力学，绝对不能这样干。你需要让程序在“后台”跑：

1. 使用 tmux（强烈推荐） 它是 Linux 下的“窗口管理器”，哪怕你断网了，下次连上来还能接回去。

# 安装
sudo apt install tmux -y

# 新建一个叫 md 的会话
tmux new -s md

# 在里面运行你的计算命令...
# 突然断网了，或者你想关电脑了...

# 下次重新 SSH 连上后，恢复之前的会话：
tmux attach -t md

2. 使用 nohup（简单的后台挂起） 如果你不想折腾 tmux，在命令前面加 nohup，结尾加 &，让它去后台自己跑：

nohup gmx mdrun -deffnm md > md.log 2>&1 &

然后你就可以关掉窗口了。想看进度，就敲 tail -f md.log。

⚠️ 资源分配警告（针对你的 96G 服务器）

你现在有 64 个 CPU 核和 96G 内存。开多个窗口同时跑任务时，一定要注意分配核数！

  • 假设你用 GROMACS 跑动力学，一条命令 gmx mdrun -nt 32（用 32 个核）。
  • 如果你同时在另一个窗口也跑一个 -nt 32 的任务，加起来正好用满 64 核。
  • 如果你开了 10 个窗口，每个都默认用全部 64 核，你的服务器会瞬间卡死（负载爆表，SSH 都敲不动）。

总结：开多窗口随便开，但脑子里要有“总资源”的概念，给每个跑计算的窗口分配好合理的 CPU 核数和内存即可。
