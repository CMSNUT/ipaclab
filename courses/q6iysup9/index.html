WSL2 + Ubantu

第一步：在 Ubuntu 里彻底重写配置文件 不要用 echo -e 了，直接用下面这行命令（使用 printf，它最稳妥，绝对不会乱加字符）：

sudo sh -c "printf '[boot]\nsystemd=true\n' > /etc/wsl.conf"

第二步：确认文件写对了 再次查看文件内容：

cat /etc/wsl.conf

必须且只能看到下面这两行（绝对不能有 -e，也不能有空行）：

[boot]
systemd=true

第三步：在 Windows PowerShell 里彻底重启 WSL 不要在 Ubuntu 窗口里操作，打开 Windows PowerShell（或者 CMD），执行：

wsl --shutdown

⚠️ 关键：执行完这个命令后，请等待至少 10 秒钟。 必须让 WSL 虚拟机完全关闭，下次启动时才会重新读取配置。

第四步：重新打开 Ubuntu 验证 重新从开始菜单打开 Ubuntu，运行：

ps -p 1 -o comm=

如果这次输出变成了 systemd，恭喜你，成功了！

✅ 成功后，继续你的 Tailscale 操作

只要 systemd 生效了，一切就好办了：

sudo systemctl enable --now tailscaled
sudo tailscale up

把终端里弹出的那个 https://login.tailscale.com/... 链接复制到远程 Windows 的浏览器里登录，就可以完成绑定。

🔑 第二步：检查 SSH 配置（允许密码登录）

为了确保你远程 Windows 能用密码顺利连进来，需要确认一下配置：

  1. 编辑配置文件：
    sudo nano /etc/ssh/sshd_config
  2. 找到 PasswordAuthentication 这一行。如果前面有 # 号（被注释了），把 # 删掉，并确保后面是 yes：
    PasswordAuthentication yes
  3. 保存并退出（按 Ctrl+O，回车，再按 Ctrl+X）。
  4. 重启 SSH 服务使配置生效：
    sudo systemctl restart ssh

💻 第三步：从远程 Windows 测试连接

现在，回到你的远程 Windows 机器上，打开 PowerShell 或 CMD，输入：

ssh aikemi@100.x.x.x

(请把 100.x.x.x 替换成你刚才在 Ubuntu 里用 tailscale ip -4 查到的 IP 地址)

可能遇到的情况：

  • 第一次连接：会提示 Are you sure you want to continue connecting (yes/no)?，输入 yes 并回车。
  • 输入密码：输入你在 Ubuntu 里的密码（注意：输入密码时屏幕上不会有任何显示，连星号都没有，这是正常的，输入完直接回车）。
  • 成功标志：提示符变成 aikemi@WIN-FOUT5C9HLE3:~$，说明你已经成功通过 Tailscale 和 SSH 连进去了！

💡 常见问题排查

  • 如果连接超时：回到 Ubuntu，输入 tailscale status，看看你的 Windows 机器是否显示为 active 或 idle。如果是 offline，检查 Windows 端的 Tailscale 是否登录并运行。
  • 如果提示 Connection refused：说明 Ubuntu 的 SSH 服务没启动，回到第一步检查 sudo systemctl status ssh 的状态。
  • 如果提示 Permission denied (publickey,password)：大概率是密码输错了，或者第二步的 PasswordAuthentication yes 没有配置好。

快去试试吧，连上之后，你就可以用 VS Code Remote-SSH 连进来，开始跑你的生信和分子动力学计算了！

使用

Tailscale配置好后，它就像一个虚拟路由器，把你远程的Windows机器和服务器WSL里的Ubuntu放进了同一个安全的私有网络（tailnet）。现在，你可以像在同一个局域网里一样直接访问它了。

📌 第一步：验证连接状态并获取IP地址

首先，需要确认两台设备都成功接入了这个虚拟网络。

  1. 在服务器端（WSL Ubuntu）：在终端运行以下命令，查看Tailscale的分配情况：

    tailscale status

    这个命令会列出你网络里的所有设备及其状态。你需要找到你的远程Windows机器的名称，并确认其状态是 active 或 idle。

  2. 获取关键的IP地址：在WSL的终端运行：

    tailscale ip -4

    这会返回一个 100.x.x.x 格式的IP地址，请记下它。这就是你远程Windows机器在虚拟网络中的“门牌号”，后续所有连接都要用到它。

🔑 第二步：配置SSH访问（用于命令行和VS Code）

SSH是你远程管理服务器和写代码的核心工具。

1. 在WSL中确保SSH服务运行 你的Ubuntu系统可能已经安装了SSH，但需要确保它正在运行。

# 检查SSH服务状态
sudo systemctl status ssh

如果状态不是 active (running)，用下面的命令启动并设置为开机自启：

sudo systemctl start ssh
sudo systemctl enable ssh

2. 从远程Windows发起连接 现在，回到你的远程Windows机器，打开PowerShell或CMD，使用刚才获取的IP地址进行连接：

# 将 100.x.x.x 替换为你记下的IP，aikemi 替换为你的Ubuntu用户名
ssh aikemi@100.x.x.x

首次连接会提示你确认服务器的指纹，输入 yes 并回车，然后输入你的Ubuntu密码即可登录。

💻 第三步：使用VS Code进行远程开发（强烈推荐）

对于代码开发和分子对接、分子动力学等计算任务，用VS Code远程连接体验最好。

  1. 安装扩展：在你的远程Windows机器上打开VS Code，在扩展商店搜索并安装 Remote - SSH 扩展。你也可以搜索并安装官方的 Tailscale 扩展，它能让你在VS Code里直接看到并连接你的设备。

  2. 配置SSH连接：

    • 按 Ctrl+Shift+P 打开命令面板，输入 Remote-SSH: Add New SSH Host...。
    • 输入连接命令：ssh aikemi@100.x.x.x（替换为你的IP和用户名）。
    • 选择默认的SSH配置文件保存。

  3. 连接并开始工作：再次打开命令面板，选择 Remote-SSH: Connect to Host...，然后选择你刚才添加的主机。VS Code会打开一个新窗口，并自动在远程的WSL中安装VS Code Server，完成后你就能像在本地一样编辑代码、打开终端了。

提示：如果连接遇到问题，确保远程的SSH配置里指定了正确的用户名，因为你的Windows用户名和WSL用户名可能不同。

💡 其他连接方式与常用命令

  • 访问Web服务：如果你在WSL的Ubuntu里启动了Jupyter Notebook或Web应用（假设端口是8888），在远程Windows的浏览器中直接访问 http://100.x.x.x:8888 即可，无需任何额外端口映射。
  • 远程桌面（RDP）：如果需要图形化操作Ubuntu桌面，可以在WSL内安装 xrdp 服务，然后从Windows用远程桌面客户端连接 100.x.x.x。不过对于你的计算需求，SSH通常是更稳定、更高效的选择。
  • Tailscale常用命令速查：
    • tailscale status：查看网络内设备状态。
    • tailscale ip -4：获取本机的Tailscale IPv4地址。
    • tailscale ping <设备名或IP>：测试与另一台设备的连通性。
    • sudo systemctl restart tailscaled：如果遇到连接异常，可以尝试重启Tailscale服务。

既然成功连进来了，接下来我教你如何把这里变成你高效跑生信和分子对接的“算力中心”。

💻 1. 终极开发体验：使用 VS Code 远程连接

虽然你现在可以在命令行里敲代码，但跑生信和写脚本，用 VS Code 最舒服。

  1. 在你当前的远程 Windows 上，打开 VS Code。
  2. 在左侧扩展商店搜索并安装 Remote - SSH。
  3. 按 F1 或 Ctrl+Shift+P 打开命令面板，输入 Remote-SSH: Connect to Host...。
  4. 选择 Add New SSH Host...，输入刚才成功的命令： ssh aikemi@100.121.21.105
  5. 按回车，选择默认的配置文件保存。之后左侧会出现一个远程连接图标，点击它，选择这个 IP 进行连接。VS Code 会自动在这个 Ubuntu 里安装服务端环境，以后你就能像用本地电脑一样在这里写代码、开终端了。

📂 2. 关于数据存放的“红线”

记住我们之前的讨论：Ubuntu 里的 /home/aikemi 实际上是存在你的 C 盘（固态，450G）里的。 跑生信和分子动力学，数据动辄几十上百 GB，千万别往 /home/aikemi 里塞，很容易把 C 盘撑爆导致服务器卡死。

建议的工作流：

  • 在 SSH 终端里，进入你的机械硬盘目录：
    cd /mnt/e/  # 进入 E 盘
mkdir -p Workspace/Bio_Project  # 建个专属工作区
cd Workspace/Bio_Project
  • 把大文件通过 Windows 资源管理器直接拖到 E 盘的 Workspace 文件夹里。
  • 在 Ubuntu 终端里直接计算（如果发现读写太慢，可以临时拷到 ~/ 下算，算完再挪回 E 盘）。

🐍 3. 开始你的计算

  • Conda 环境：你之前装的 Miniconda 已经好了，在终端输入 conda create -n md_env python=3.9 就能建个专门跑分子动力学的环境（比如装 openmm 或 mdtraj）。
  • Docker：如果你想跑一些打包好的生信工具，直接敲 docker run ...。

⚠️ 两个极其重要的提醒

  1. 不要升级系统：你在登录时看到了 New release '24.04.5 LTS' available.。千万不要执行 do-release-upgrade！ WSL 跨大版本升级极易导致系统崩溃和网络挂掉，22.04 是公认最稳的 WSL 版本，保持现状即可。
  2. 保持 WSL 运行：如果你把服务器上的 Ubuntu 窗口全关了，WSL 休眠后 SSH 就会断（Connection reset by peer）。如果你需要长时间挂机跑动力学模拟，记得在服务器上开一个 Ubuntu 窗口挂着，或者通过 Windows 计划任务配置 WSL 常驻。

现在，你可以试着在 Windows 的 PowerShell 里敲一下 exit 退出当前 SSH，然后用 VS Code 连进去，建一个 .py 或 .sh 脚本跑个 Hello World 试试看！有问题随时找我。

这段配置非常有用，千万不要删！

这通常是程序员为了在公司或学校的网络环境（防火墙）下，依然能顺利使用 SSH 访问 GitHub 而添加的。

💡 它是干嘛的？

简单来说，GitHub 默认的 SSH 端口是 22，但很多校园网或公司网络会封禁 22 端口，导致你 git clone 或 git push 失败。 这段配置的作用是：当你访问 github.com 时，自动强制走 443 端口（也就是 HTTPS 的端口，通常不会被封禁）。

  • Hostname ssh.github.com 和 Port 443：这就是 GitHub 官方提供的备用通道。

🚨 为什么它会导致你 VS Code 报错？

因为 VS Code 的 Remote-SSH 插件会读取这个配置文件。它看到了 Host github.com，就以为这也是一个你可以连接的“远程服务器”，于是你在选的时候，可能不小心点到了它，或者 VS Code 默认尝试去连它。

但 GitHub 的服务器是不允许你连进去当电脑用的（它不跑 VS Code Server），所以直接就报错 Could not establish connection to "github.com" 了。

🛠️ 怎么解决？

方法一：直接无视它（最简单） 既然你知道了 github.com 是个捣乱的配置，下一次在 VS Code 里连接时，看仔细一点，绝对不要选它。 在 VS Code 命令面板输入 Remote-SSH: Connect to Host... 后，直接输入你的服务器 IP： aikemi@100.121.21.105

方法二：给它加个名字，彻底防止点错 你可以用记事本打开 C:\Users\Administrator\.ssh\config，在文件最下面加上几行，专门给你的服务器起个名字：

Host WSL-Server
    HostName 100.121.21.105
    User aikemi
    Port 22

(注意：不要动上面那段 github 的配置，直接在下面追加)

保存后，再打开 VS Code 的 Remote-SSH 插件，下拉列表里就会多出一个叫 WSL-Server 的选项。你以后只点这个选项，就不会再连错到 GitHub 去了。

你的代码和文件保存在 Ubuntu 上。

这是一个非常核心的概念：在你的这套架构里，远程 Windows 上的 VS Code 只是一个“带屏幕的遥控器”。

🖥️ 它是怎么工作的？

  1. 你在远程 Windows 的 VS Code 里敲代码、点保存。
  2. VS Code 通过网络（Tailscale 虚拟 IP）把代码内容发送给服务器里的 Ubuntu。
  3. Ubuntu 负责真正把文件写进硬盘里。
  4. 你在 VS Code 里打开的终端，实际上也是运行在 Ubuntu 里的，不是你的远程 Windows 机器。

所以，你的代码文件物理上存放在服务器的硬盘里，和你的远程 Windows 机器本地没有任何关系（哪怕你把远程 Windows 关机了，服务器上的代码依然在）。

⚠️ 结合你的服务器情况，到底存在哪个盘？（极其重要）

由于你是在 Ubuntu 里操作，文件到底存在哪，取决于你刚才在 VS Code 里打开的文件夹路径：

情况一：你打开的是 ~/ 或 /home/aikemi 下的目录

  • 物理位置：它实实在在存在服务器的 C 盘（固态硬盘）里（就是那个 ext4.vhdx 虚拟磁盘文件）。
  • 建议：适合存放你写的代码脚本（如 .py, .sh 文件）、小的配置文件。固态硬盘读写快，代码体验好。但绝对不能放几百 G 的生信原始数据！

情况二：你打开的是 /mnt/e/ 下的目录（强烈推荐）

  • 物理位置：它存在服务器的 E 盘（4.95TB 机械硬盘）里。
  • 建议：如果你要处理分子对接、动力学模拟，直接把项目文件夹建在 /mnt/e/projects 下。几十个 G 的轨迹文件、庞大的测序数据放在这里，完全不用担心撑爆 C 盘。

💡 新手极易踩的坑（千万不要做）

千万不要把你远程 Windows 机器上的代码文件夹，直接拖拽到 VS Code 的左侧窗口里！

如果你在 VS Code 里选择 File -> Open Folder...，然后选择了你本地（远程 Windows）的 C:\Users\Administrator\Desktop\MyCode： VS Code 会直接打开你本地的文件夹。你在这修改的代码，依然保存在你本地 Windows 上，Ubuntu 根本看不见，也就无法用服务器的算力去运行它。

正确姿势： 每次连上远程后，点击 VS Code 的 文件 -> 打开文件夹，在弹出的路径框里输入 /home/aikemi/ 或者 /mnt/e/projects。这样，你的代码才真正进入了 Ubuntu 的怀抱。

“半天没连上”是大家第一次用 VS Code 连远程服务器时最常遇到的问题。别着急，大概率是因为它正卡在后台下载组件的环节。

你之前报错说连不上 github.com，说明你的网络下载微软/GitHub 的文件极慢。VS Code 连上 Ubuntu 后，必须在 Ubuntu 里下载一个约 100MB 的 vscode-server 组件，如果下载太慢，它就会一直转圈或者卡死。

我们可以按以下步骤来排查和解决：

🔍 第一步：看它到底卡在哪了

  1. 在 VS Code 窗口底部，点击 “输出” (Output) 面板（如果没看到，按 Ctrl+Shift+U）。
  2. 在输出面板右侧的下拉菜单里，选择 Remote - SSH。
  3. 看里面滚动的日志：
    • 如果看到 Downloading VS Code Server...，说明网络卡住了，下载极慢。
    • 如果看到一直在 Waiting for server log...，通常是连接上了，但在后台启动失败。
    • 如果直接报错 Connection timeout，说明 SSH 层面断开了。

💡 第二步：基础网络验证

打开你远程 Windows 的 PowerShell，输入：

ping 100.121.21.105

如果一直在请求超时，说明你的 Tailscale 掉线了或者服务器那边的 WSL 休眠了。去服务器上重新打开一下 Ubuntu 终端。

如果 ping 得通，继续在 PowerShell 里用命令行连：

ssh aikemi@100.121.21.105

如果命令行几秒钟就能秒进，说明网络没问题，纯粹是 VS Code 搞事情（下载组件太慢）。

🚀 第三步：终极大招 —— 手动离线安装组件

既然网络下载慢，我们直接给它“空投”过去，绕过网络下载。

1. 获取 Commit ID 在你的 VS Code 界面，按 F1 打开命令面板，输入 About，选择 Help: About。 在弹出的窗口中，找到 Commit 那一行，复制后面那一长串字母和数字（例如 08d4889f9ec4a1685d257b9b95de036c8e1ce1e5）。

2. 在 Windows 上手动下载 打开你的 Windows 浏览器，把下面这个链接的 你的CommitID 替换成刚才复制的长串： https://update.code.visualstudio.com/commit:你的CommitID/server-linux-x64/stable 下载下来会得到一个名为 vscode-server-linux-x64.tar.gz 的压缩包。

3. 传进 Ubuntu 并解压 你可以用 MobaXterm 或者 WinSCP 把这个压缩包传到 Ubuntu 的 /home/aikemi 目录下。 然后在你的 Ubuntu 终端（不是在 VS Code 里，单独打开一个终端窗口）执行：

# 创建目录（注意替换成你的Commit ID）
mkdir -p ~/.vscode-server/bin/你的CommitID

# 解压（注意替换成你的Commit ID和实际文件名）
tar -zxvf ~/vscode-server-linux-x64.tar.gz -C ~/.vscode-server/bin/你的CommitID --strip-components 1

4. 重新连接 回到 Windows 的 VS Code，按 F1，选择 Remote-SSH: Kill VS Code Server on Host... 清理一下，然后重新点连接。 因为文件已经存在了，它一秒钟就能启动，不会再卡住了。

🔄 备选方案：如果你觉得手动下载太麻烦

有时候服务器网络只是间歇性抽风。你可以试试在 VS Code 的设置里改一下重试机制：

  1. 按 Ctrl+, 打开设置。
  2. 搜索 remote.SSH.connectTimeout。
  3. 把默认的 15 秒改成 60 秒或者更高。
  4. 关掉 VS Code 重新打开，再给它一次机会，多点耐心等一下。

你可以先看看底部的“输出”日志里显示到了哪一步，或者直接在 PowerShell 里试试 ssh 能不能秒连。告诉我结果，我帮你精准定位！

这在 WSL 用户里是非常普遍的痛点！因为你的 Ubuntu 跑在自己专属的 Windows 服务器里，安全性完全可控，所以最爽的解决办法就是给当前用户 aikemi 开启 sudo 免密。

开启后，你敲任何 sudo 命令都不用再输密码了。只需设置一次，永久生效。

🛠️ 开启 sudo 免密的步骤：

第一步：安全地编辑 sudo 配置文件 在 Ubuntu 终端输入以下命令（千万不要直接用 nano 编辑，一定要用 visudo，它会帮你检查语法，防止你打错字导致系统权限彻底锁死）：

sudo visudo

第二步：添加免密规则 进入编辑界面后，用键盘方向键翻到最下面，找到类似 %sudo ALL=(ALL:ALL) ALL 这一行，然后在这行的下面，添加你专属的免密规则：

aikemi ALL=(ALL) NOPASSWD: ALL

(输入后，这行字会显示在屏幕上。)

第三步：保存并退出 和之前一样，按 Ctrl + O（保存），按回车确认，再按 Ctrl + X（退出）。

第四步：验证 随便敲一个需要 sudo 的命令，比如：

sudo apt update

你会发现它直接就跑了，不再问你要密码了！

💡 进阶小贴士（VS Code 里彻底告别密码）

既然你都用 VS Code 了，其实平时根本不需要单独开 Ubuntu 窗口。在 VS Code 顶部菜单栏选择 “终端” -> “新建终端”，直接在 VS Code 里敲命令即可。现在你开启了免密，VS Code 里的终端和写脚本自动化运行的时候，也就再也不会卡在输密码这一步了。
