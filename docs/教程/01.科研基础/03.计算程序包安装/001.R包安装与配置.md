## ⚙️ 安装前的必要配置

在开始安装前，建议先配置好国内镜像，以保证下载速度的稳定。在 RStudio 的 Console 中执行以下代码：

```r
# 配置 CRAN 和 Bioconductor 的国内镜像 (以清华大学源为例)
options(repos = c(CRAN = "https://mirrors.tuna.tsinghua.edu.cn/CRAN/"))
options(BioC_mirror = "https://mirrors.tuna.tsinghua.edu.cn/bioconductor/")

# 确认镜像配置
options("repos")
options("BioC_mirror")
```

### 🐍 1. 连接 Python 的包：`reticulate`
`reticulate` 包是 R 与 Python 交互的核心。安装后，需要明确指定使用你已创建好的 `cadd_env` 虚拟环境。

```r
# 从 CRAN 安装
install.packages("reticulate")

# 加载并指定你的 conda 环境
library(reticulate)
use_condaenv("cadd_env", required = TRUE)

# 验证配置的 Python 环境
py_config()
```



在同一个 R 会话中，`reticulate` 有一个核心限制：**一旦初始化了某个 Python 环境，就无法直接在当前会话中切换到另一个完全不同的环境**。这是因为 R 进程加载了特定 Python 解释器的动态库，无法在内存中“卸载”它。

不过，如果你的代码逻辑确实需要调用多个虚拟环境（比如 `cadd_env` 用于分子对接，另一个环境用于机器学习），有几种成熟的解决方案。

### 🛠️ 方案一：使用 `callr` 包进行会话隔离（最推荐）

这是最干净、最稳定的方案。`callr` 包允许你在**独立的 R 进程中**运行代码，每个进程都可以绑定不同的 Python 环境，互不干扰。

**操作流程：**

1.  **确保已安装 `callr`**：`install.packages("callr")`
2.  **编写脚本**：创建两个独立的 R 脚本文件，分别用于不同的环境。

    *   `script_cadd.R` (使用 cadd_env)：
        ```r
        # 这个脚本会在独立的 R 进程中运行
        library(reticulate)
        use_condaenv("cadd_env", required = TRUE)
        
        # 在这里执行你的 cadd_env 相关操作
        rdkit <- import("rdkit")
        print(py_config()$python)
        ```
    
    *   `script_ml.R` (使用另一个环境，例如 ml_env)：
        ```r
        # 这个脚本也会在另一个独立的 R 进程中运行
        library(reticulate)
        use_condaenv("ml_env", required = TRUE) # 假设你的机器学习环境叫 ml_env
        
        # 在这里执行 ml_env 相关操作
        sklearn <- import("sklearn")
        print(py_config()$python)
        ```

3.  **在主 R 会话中调用 `callr`**：
    ```r
    library(callr)
    
    # 在后台独立进程中运行 cadd_env 的脚本
    result_cadd <- rscript("path/to/script_cadd.R", show = TRUE)
    
    # 在另一个独立进程中运行 ml_env 的脚本
    result_ml <- rscript("path/to/script_ml.R", show = TRUE)
    ```

**优点**：环境彻底隔离，互不污染，非常稳定。
**缺点**：进程间通信需要通过文件或返回值进行，稍微繁琐。

### 📦 方案二：`reticulate` 的多环境搜索（有限支持）

`reticulate` 的 `import()` 函数支持提供一个环境名称的**字符向量**，它会按顺序搜索这些环境来加载模块。但这主要适用于**加载模块**，而不是完全隔离的运行环境。

```r
library(reticulate)

# 尝试在多个环境中寻找并加载模块
# 注意：这仍然是在同一个 Python 解释器进程中，只是扩展了搜索路径
import("some_module", delay_load = list(environment = c("cadd_env", "ml_env")))
```

这种方式**不能**让你同时运行两个环境的不同代码，它只是在找不到模块时，去另一个环境的路径里找找看。

### 🐍 方案三：通过 `import_from_path` 直接加载模块

如果两个环境的 Python 主版本兼容，你可以尝试用 `import_from_path` 直接从另一个环境的 `site-packages` 目录加载模块。

```r
library(reticulate)
# 先初始化主环境
use_condaenv("cadd_env", required = TRUE)

# 直接从另一个环境的路径加载模块
ml_module <- import_from_path("sklearn", path = "/path/to/ml_env/lib/python3.x/site-packages/")
```

**风险**：如果两个环境依赖的底层库版本不一致，极易导致冲突或崩溃，**不推荐用于生产环境**。

### 🐳 方案四：终极隔离——Docker 或独立脚本

对于极度复杂、依赖冲突严重的场景，**最彻底**的方案是：

1.  **用独立的 Python 脚本**，配合 `system()` 或 `system2()` 从 R 中调用，每个脚本的 Shebang（`#!/usr/bin/env python`）指向不同的环境。
2.  **将不同环境的任务封装进不同的 Docker 容器**，R 通过 API 或文件进行调度。

### 💎 总结与建议

| 方案                  | 隔离程度     | 易用性 | 推荐场景                               |
| :-------------------- | :----------- | :----- | :------------------------------------- |
| **`callr` 包**        | **完全隔离** | 中等   | **最推荐**，需要同时运行多个环境的代码 |
| `import()` 多环境搜索 | 无隔离       | 简单   | 仅用于查找模块，不能隔离运行           |
| `import_from_path`    | 无隔离       | 复杂   | 版本兼容时，快速借用模块               |
| **独立脚本/Docker**   | **完全隔离** | 复杂   | 生产环境，依赖冲突严重                 |

**建议你先尝试方案一（`callr`）**，它为 R 语言原生设计，能完美解决“一个会话，多个环境”的需求。如果你在实现过程中遇到具体的报错，可以把信息发给我，我再帮你分析。

## ⚡ 批量安装脚本

**建议分块执行**，每装完一批用 `library()` 验证，便于定位依赖问题。

```r
# ==========================================
# 0. 镜像配置 + 基础工具

## 关于并行

在RStudio中启动并行计算，核心是使用R的并行包，将任务分配给服务器的多个CPU核心来执行。对于你之前安装的 `tidymodels` 和 `mlr3` 等建模框架，也有特定的并行化配置方法。

---

### 🔍 并行计算前需要了解的事

在开始配置前，有几个基本概念需要明确：

*   **不是所有代码都能自动并行**：除了少数线性代数运算，大部分代码需要你**显式地**修改，才能利用多核优势。
*   **任务需要可独立拆分**：并行的前提是计算任务可以拆分成多个独立的部分，例如对数据的不同子集、模型的不同超参数组合等。
*   **并非核心越多越快**：并行化本身有开销，对于非常小的任务，使用过多核心可能反而降低效率。

---

### 🛠️ 基础并行计算：核心工具包

R语言有几个核心的并行计算包，它们各有侧重，可以满足不同场景的需求。

| 工具包/包组合                 | 核心定位与适用场景                                           | 基本使用模式                                                 |
| :---------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **`future` + `future.apply`** | **现代、统一的并行框架**，语法简洁，是当前社区的主流选择。   | 设置 `plan(multisession)` 后，用 `future_lapply()` 等替代 `lapply()`。 |
| **`foreach` + `doParallel`**  | **经典循环并行化**方案，通过 `%dopar%` 操作符实现。          | 用 `foreach()` 构建循环，`%dopar%` 执行，并用 `registerDoParallel()` 注册后端。 |
| **`parallel`**                | **R基础包**，提供最底层的并行功能，如 `mclapply()`（仅限Linux/macOS）和 `parLapply()`。 | 创建集群 `makeCluster()`，使用 `parLapply()` 等，最后 `stopCluster()` 关闭。 |

#### 1. 通用并行：`future` 框架
`future` 框架是目前最推荐的通用并行方案，它提供了一致的API，可以轻松切换串行和并行执行。

```r
# 1. 安装并加载必要的包
install.packages(c("future", "future.apply"))
library(future)
library(future.apply)

# 2. 设置并行计划：使用所有可用的物理核心
# 'multisession' 是跨平台推荐的策略
plan(multisession, workers = availableCores())

# 3. 用 future_lapply 替代 lapply 来并行化
# 假设有一个耗时函数 slow_function
results <- future_lapply(1:100, function(i) {
  Sys.sleep(0.1) # 模拟耗时操作
  i^2
})

# 4. 查看结果
head(results)

# 5. 用完后，建议恢复串行计划
plan(sequential)
```
`plan(multisession)` 会启动多个后台R进程来并行工作，非常适合在RStudio中交互式使用。在Linux系统上，`plan(multicore)` 理论上开销更小，但在RStudio中有时会不稳定，`multisession` 是更安全的选择。

#### 2. 循环并行：`foreach` 组合
如果你习惯写循环，`foreach` + `doParallel` 的组合非常直观。

```r
# 1. 安装并加载
install.packages(c("foreach", "doParallel"))
library(foreach)
library(doParallel)

# 2. 检测核心数并注册并行后端
num_cores <- detectCores() - 1 # 保留一个核心给系统
cl <- makeCluster(num_cores)
registerDoParallel(cl)

# 3. 使用 %dopar% 执行并行循环
results <- foreach(i = 1:100, .combine = rbind) %dopar% {
  # .combine 参数指定如何合并结果，这里用 rbind 按行合并
  data.frame(id = i, value = i^2)
}

# 4. 循环结束后，务必关闭集群
stopCluster(cl)
print(head(results))
```
**注意**：`makeCluster()` 和 `stopCluster()` 必须成对出现，否则会留下僵尸进程占用资源。

---

### 🚀 在建模框架中启用并行

你之前安装的 `tidymodels` 和 `mlr3` 等框架，内部已经集成了并行支持，通常只需简单设置即可开启。

#### 1. `tidymodels` 并行化
`tidymodels` 的 `tune` 包默认**不启用**并行，需要你手动激活。

```r
library(tidymodels)
library(future)

# 1. 设置并行计划
plan(multisession, workers = availableCores() - 1)

# 2. 在 tune_grid() 或 fit_resamples() 中启用并行
# 关键参数是 control_grid(allow_par = TRUE)
tune_results <- tune_grid(
  ...,
  control = control_grid(allow_par = TRUE) # 允许并行
)

# 3. 并行结束后，恢复串行
plan(sequential)
```
核心是 `control_grid(allow_par = TRUE)`。`tune` 会利用 `future` 框架，将不同超参数组合或重采样折叠分配到不同核心上执行。

#### 2. `mlr3` 并行化
`mlr3` 同样通过 `future` 框架实现并行，用于模型训练、重采样、调参等任务。

```r
library(mlr3)
library(future)

# 1. 设置并行计划
plan(multisession, workers = availableCores() - 1)

# 2. 正常创建并训练你的任务，mlr3会自动利用并行后端
task <- tsk("iris")
learner <- lrn("classif.ranger", num.threads = 1) # 避免learner内部再并行
learner$train(task)

# 3. 对于重采样等操作，并行会自动生效
rr <- resample(task, learner, rsmp("cv", folds = 5))

# 4. 恢复串行
plan(sequential)
```
**重要提示**：当使用 `mlr3` 进行并行时，应将学习器内部的线程数（如 `ranger` 的 `num.threads`）设为 `1`，避免“外部并行、内部也并行”的冲突，导致性能下降。

### 🖥️ RStudio Server 层面的资源调度

除了在代码中控制并行，如果通过RStudio Server的Web界面启动会话，也可以在启动时申请更多CPU核心。

*   **HPC/集群环境**：在启动RStudio Server的作业提交表单中，通常有 **CPU Cores** 选项，用于指定分配给该会话的核心数。选择多核心后，RStudio Server可能会自动设置 `OMP_NUM_THREADS` 环境变量，为支持OpenMP的底层计算库提供并行能力。
*   **本地服务器**：如果你直接管理RStudio Server，可以通过配置文件 `/etc/rstudio/profiles` 来为特定用户或用户组设置 **CPU亲和性（cpu-affinity）**，将他们的会话绑定到指定的核心上，实现资源隔离。

---

### 💡 关键注意事项与最佳实践

1.  **避免嵌套并行**：不要在并行任务内部，再调用另一个会并行的函数（例如，在 `foreach` 循环里使用内部多线程的 `ranger`）。这会导致资源过载和性能下降。
2.  **管理内存使用**：每个并行工作进程都会消耗独立的内存。处理大型数据集时，需要监控内存使用，避免因内存耗尽而崩溃。
3.  **选择合适的工作进程数**：通常建议设置为**物理核心数 - 1**，为操作系统保留一个核心，以保证系统响应。
4.  **任务粒度要适中**：每个并行任务的计算量不宜过小，否则进程间通信和调度的开销会抵消并行带来的收益。
5.  **注意包的兼容性**：少数R包（如`rJava`、`keras`）与显式并行化不兼容，使用时会自动回退到串行模式。

### 🎛️ 上游调控：推断“谁在指挥”

上游调控分析的核心是**从基因表达变化反推调控它们的上游因子**，主要包括**转录因子（TF）活性**和**信号通路活性**。

#### 1. 转录因子调控网络：SCENIC 及其相关工具

| 包名 / 工具    | 定位与适用场景                                               | 教程 / 主页                                                  | 关键说明                                                     |
| :------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **SCENIC**     | **单细胞转录因子调控网络推断的“金标准”**。通过共表达模块 + motif富集，构建TF-target regulon，并评分细胞级别的调控活性。 | [详细教程](https://rdrr.io/github/aertslab/SCENIC/f/vignettes/SCENIC_Running.Rmd) | 流程较长，依赖 loom 格式和 cisTarget 数据库，计算资源需求较高。 |
| **RcisTarget** | **从基因列表反向推断上游TF**。基于motif富集分析，鉴定基因集背后可能的调控转录因子，适合**Bulk RNA-seq**的差异基因上游分析。 | [实战教程](https://cloud.tencent.cn/developer/article/2399213) | 需要准备物种对应的 motif 数据库。                            |
| **decoupleR**  | **通用的调控因子活性推断框架**。可通过整合 **CollecTRI（转录调控）**、**PROGENy（通路）** 等资源，从表达矩阵估算TF或通路活性，灵活性很高。 | [官方文档](https://saezlab.github.io/decoupleR/)             | 需要配合资源包（如 `decoupleR::get_collectri()`）使用。      |
| **RegEnrich**  | **基因调控富集分析**。专门用于从差异表达结果中识别关键调控因子，并构建调控网络。 | Bioconductor 页面                                            | 适合与差异表达分析（如 `DESeq2`）的结果直接衔接。            |

#### 2. 信号通路活性推断：PROGENy

| 包名        | 定位与核心优势                                               | 教程 / 主页                                                  | 关键说明                                                    |
| :---------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :---------------------------------------------------------- |
| **PROGENy** | **信号通路活性推断**。提供**14条**关键信号通路的基因signature，通过矩阵运算从表达数据推断通路活性水平。 | [Bioconductor页面](https://bioconductor.posit.co/packages/PROGENy/) | 通常与 **`decoupleR`** 配合使用，后者提供了统一的推断接口。 |

**选型建议**：
*   **单细胞数据、需要精细的TF调控网络**：**`SCENIC`** 是标准答案。
*   **Bulk RNA-seq、想从差异基因快速推断上游TF**：**`RcisTarget`** 或 **`decoupleR`** + `CollecTRI` 资源是更轻量的选择。
*   **希望同时获得TF和通路活性**：**`decoupleR`** + **`PROGENy`** 的组合提供了统一的框架。

## 重来

批量安装报错通常是**系统级底层编译依赖缺失**导致的。你的服务器是全新的 Ubuntu 环境，许多 R 包（如 `tidyverse`、`sf`、`xml2` 等）需要底层的 C/C++ 库（如 `libxml2`、`libcurl`、`libssl`）才能编译成功。

放弃逐个 `install.packages()` 手动修错，推荐用两步走：**先补全系统级依赖，再用现代化的包管理器统一安装**。

---

### 🐧 第一步：一次性补全 Ubuntu 系统依赖

在 **Ubuntu 终端**（不是 RStudio 里）执行以下命令，安装 R 编译所需的全部基础库：

```bash
sudo apt update
sudo apt install -y build-essential gfortran default-jdk \
  libcurl4-openssl-dev libssl-dev libxml2-dev \
  libfontconfig1-dev libfreetype6-dev libpng-dev libtiff-dev libjpeg-dev \
  libcairo2-dev libharfbuzz-dev libfribidi-dev \
  libglpk-dev libgmp-dev libfftw3-dev libmagick++-dev \
  cmake libudunits2-dev libgdal-dev gdal-bin libgeos-dev libproj-dev libsqlite3-dev \
  libnode-dev libsodium-dev tcl tk tk-dev tk-table
```

> **说明**：`default-jdk` 为 `rcdk` 提供 Java 环境；`libgdal-dev` 等地理空间库是 `sf` 系列包的基础；`libxml2-dev`、`libcurl4-openssl-dev` 是网络爬取和解析包（如 `GEOquery` 依赖）的编译前提。

---

### 📦 第二步：用 `pak` 替代 `install.packages()`（最省心）

`pak` 是 R 社区新一代的包管理器，能**自动解析 CRAN/Bioconductor/GitHub 的完整依赖树**，并按正确顺序安装，避免“先装子包再装父包”的顺序错误。

在 **RStudio Console** 中安装 `pak`：

```r
install.packages("pak", repos = "https://r-lib.github.io/p/pak/stable/")
```

安装完成后，即可用 `pak::pkg_install()` 替代 `install.packages()`。`pak` 还支持 `pak::pkg_sysreqs()` 自动检测系统级依赖，如果后续某个包仍报错，可以先用它查漏：

```r
pak::sysreqs_db_update()

pak::pkg_sysreqs("你的包名")
```

---

### 🚀 第三步：按依赖层级分步安装（避免连锁报错）

即使是 `pak`，一次性安装几十个包也可能因某个底层依赖编译失败而整体中断。建议**按“底层 → 中层 → 上层”的顺序分批安装**，每批完成后先验证能否加载，再继续下一批。

### 🔬 亚细胞定位

**R 原生能做的**和**真正前沿的方法**之间存在明显断层，需要分开看待。

#### R 原生：实验数据驱动的定位推断

**`pRoloc`**（Bioconductor）是空间蛋白质组学的标准 R 框架。它不直接“预测”序列的定位，而是用**定量质谱数据 + 机器学习**推断蛋白的亚细胞定位，并提供丰富的可视化工具。

```r
BiocManager::install("pRoloc")
```

#### 序列预测的前沿：蛋白质语言模型（Python 桥接）

亚细胞定位预测的 state-of-the-art 已经转向蛋白质语言模型。**DeepLoc 2.0** 基于预训练蛋白质语言模型，在多标签亚细胞定位预测上达到了领先水平。类似地，ProtT5、ESM-2 等模型也被用于提取序列 embedding，再训练分类器，在 DeepLoc 2.0 数据集上可达到约 **91%** 的准确率。

**这些工具没有成熟的 R 原生包**，现实路径是通过 `reticulate` 桥接：

1. 在 `cadd_env` 或新建 Python 环境中安装依赖：`pip install fair-esm transformers torch`（或直接调用 DeepLoc 的在线/本地版本）。
2. 在 R 中用 `reticulate` 调用 Python 提取 embedding 或直接获取预测结果。
3. 回到 R 中进行下游统计与可视化。

2. **`Protein2Tissue` 仍在 GitHub 开发阶段**，尚未正式进入 Bioconductor。安装时如果 `remotes::install_github` 因网络失败，可以尝试通过镜像代理。
3. **亚细胞定位的现实预期**：`pRoloc` 解决的是“**我有空间蛋白质组学质谱数据，如何推断定位**”的问题；如果你要做的是“**给一段蛋白序列，预测它去哪里**”，这属于蛋白质语言模型的领域，R 只能作为下游整合层，不要期待 `pRoloc` 直接完成序列预测。

```

### ⚠️ 如果重启后还是登录不进去？（急救方案）

结合你之前修改了超时配置导致登录卡死的情况，如果这次重启后网页依然打不开或一直转圈，请按顺序执行以下“急救三步”：

**1. 先强制停止服务**
```bash
sudo rstudio-server stop
```

**2. 清理卡死的用户会话缓存**
*(注意：这只会清空你未保存的内存变量，不会删除你写好的代码文件)*
```bash
rm -rf ~/.local/share/rstudio/sessions
```

**3. 再次启动服务**
```bash
sudo rstudio-server start
```

然后打开浏览器，按 `F5` 刷新，或者用**无痕模式**（`Ctrl+Shift+N`）重新访问 `http://你的IP:8787`。

如果还是不行，直接看报错日志：
```bash
sudo tail -n 50 /var/log/rstudio/rstudio-server/rserver.log
```
清理 RStudio 的日志非常简单，但需要区分**用户级别的会话日志**和**系统级别的服务日志**。清理前，最好先停止 RStudio 服务，避免文件被占用或清理后进程报错。

以下是完整的清理步骤：

---

### 🧹 1. 清理用户级别的 R 会话日志（最常用）

这些日志保存在你的家目录下，记录了你每次登录 RStudio 时的详细运行情况。随着使用时间变长，这些日志可能会占几百 MB 甚至几个 GB 的空间。

在 Ubuntu 终端执行：

```bash
# 进入日志目录
cd ~/.local/share/rstudio/log/

# 查看当前日志文件大小，确认占用情况
ls -lh

# 删除所有的 rsession-*.log 和 rserver-*.log 文件
rm -f rsession-*.log rserver-*.log

# （可选）如果你想把文件夹里所有历史日志都清空（包括 .log.1, .log.2 等轮转文件）
rm -f *
```

*注意：清理用户日志**不会**影响你的代码、项目或 R 包的安装，仅仅是删除了诊断记录。*

---

### 🗑️ 2. 清理系统级别的 RStudio Server 服务日志

这些是系统服务的日志，通常位于 `/var/log` 下，需要 `sudo` 权限才能操作。

```bash
# 查看系统日志大小
sudo ls -lh /var/log/rstudio/rstudio-server/

# 清空系统服务日志文件（推荐使用 truncate 或 echo，而不是直接 rm，避免服务找不到文件）
sudo truncate -s 0 /var/log/rstudio/rstudio-server/rserver.log
sudo truncate -s 0 /var/log/rstudio/rstudio-server/rserver.log.*

# 如果还有 access.log 等，也可以一并清空
sudo truncate -s 0 /var/log/rstudio/rstudio-server/*.log
```

*(或者直接运行 `sudo rstudio-server log-rotate` 来强制轮转并清理旧日志)*

---

### 🔄 3. 清空系统 systemd 日志（可选，视情况）

RStudio 服务的启动错误也会被记录在系统的 `systemd` 日志里（即 `journalctl` 日志）。如果你之前排查报错时发现 `journalctl` 占用了大量空间，可以清理它：

```bash
# 查看 journal 占用空间
journalctl --disk-usage

# 只保留最近 2 天的日志
sudo journalctl --vacuum-time=2d

# 或者限制总大小为 200MB
sudo journalctl --vacuum-size=200M
```

---

### ⚠️ 清理后的注意事项

1. **建议先停服务再清理**：如果你想彻底清空，可以执行 `sudo systemctl stop rstudio-server`，清理完后再 `sudo systemctl start rstudio-server`。这样能避免服务在运行状态下因日志文件被删而报错。
2. **日志是排错的依据**：如果你目前还在排查 `jsonrpc error 1` 的问题，**建议不要马上删日志**，而是先 `tail -n 100` 把关键报错信息复制下来，或者重命名保存一份（例如 `mv rsession-aikemi.log rsession-aikemi.log.bak`），然后再清理。
3. **如果日志文件巨大且无法删除**：可能是因为某个 R 进程卡死，一直占用着文件句柄。此时先 `ps -u aikemi | grep rsession | awk '{print $1}' | xargs kill -9` 杀进程，然后再删文件。

清理完日志后，重启服务，再次尝试登录 RStudio，看看 `jsonrpc` 错误是否消失。如果问题依旧，你需要将刚生成的**最新日志**中带有 `ERROR` 的行发给我，因为清理旧日志本身并不解决连接问题，它只是为了让你看清现在的错误。



清理安装包文件，能为你腾出不少 WSL 虚拟磁盘的空间。由于你之前编译了 R、装了 RStudio、Miniconda 和大量的 R 包，留下的“垃圾”主要分为两类：**系统缓存**和**手动下载的源码/安装包**。

请按照以下步骤，在 **Ubuntu 终端**中依次执行（注意看提示，别误删了重要文件）：

### 🧹 1. 清理 APT 下载的 `.deb` 缓存包
系统在安装软件时，会把安装包全留在 `/var/cache/apt/archives/`。直接清空它：
```bash
sudo apt clean
```
*顺便清理一下不再需要的依赖（⚠️ **警告**：执行时看一眼屏幕提示，如果提示要卸载 `build-essential`、`gcc` 等编译工具，**立刻按 `N` 取消！** 否则你以后装 R 包会全报错）：*
```bash
sudo apt autoremove --purge
```

### 🗑️ 2. 清理你手动下载的“大件”
进入你的家目录，把之前下载的安装包和源码全部删掉：
```bash
cd ~

# 删除 R 源码压缩包和解压后的文件夹
rm -rf ~/R-4.6.2.tar.gz ~/R-4.6.2

# 删除 RStudio Server 的 deb 安装包（如果你放在家目录了）
rm -f ~/rstudio-server-*.deb

# 删除 Miniconda 的 sh 安装包
rm -f ~/Miniconda3-latest-Linux-x86_64.sh

# 删除 Ubuntu 的离线安装包（AppxBundle）
rm -f ~/Ubuntu*.AppxBundle

# 清理 Conda 的缓存包
conda clean -a -y
```

### 📦 3. 清理系统日志和临时文件（可选）
你刚才排查 RStudio 错误可能产生了一些日志，顺手清理一下：
```bash
# 清理临时文件夹
sudo rm -rf /tmp/*

# 清理 systemd 日志，只保留最近2天的
sudo journalctl --vacuum-time=2d
```

### 🚨 终极必杀技：如何让 Windows C盘 真正腾出空间？
**这是一个极易被忽略的坑！**
在 WSL2 里用 `rm` 删除了文件，**Windows 的 C 盘空间并不会立刻变多**。因为 WSL2 的虚拟磁盘（`ext4.vhdx`）只会变大，不会自动缩小。

**你必须回到 Windows 宿主机上执行压缩操作：**
1. 打开 **Windows PowerShell**（普通模式即可，不需要管理员）。
2. 彻底关闭 WSL：
   ```powershell
   wsl --shutdown
   ```
3. 打开 Windows 的“命令提示符” (CMD) 或 PowerShell（管理员），输入以下命令进入磁盘管理：
   ```powershell
   diskpart
   ```
4. 在弹出的 `DISKPART>` 提示符下，依次输入以下三行（**注意把路径替换成你真实的 `.vhdx` 路径**，通常在 `C:\Users\Administrator\AppData\Local\Packages\...\LocalState\ext4.vhdx`）：
   ```diskpart
   select vdisk file="C:\Users\Administrator\AppData\Local\Packages\CanonicalGroupLimited.Ubuntu22.04LTS_79rhkp1fndgsc\LocalState\ext4.vhdx"
   compact vdisk
   exit
   ```
   *(这个过程可能需要几分钟，完成后你会发现 C 盘瞬间多出了几十个 G 的空间！)*

你可以先用 `df -h /` 看一下现在 Ubuntu 里还有多少空间。清理完、压缩完，C盘的空间就彻底释放了。



明白了，你要清理的是 **RStudio 自身产生的缓存文件**，而不是系统包或源码。这些文件主要分布在用户家目录的隐藏文件夹里，清理它们可以释放空间，并且有时能解决 RStudio 启动或连接的“玄学”问题。

请按以下步骤操作，**建议先停止 RStudio 服务**，避免文件被占用：

```bash
# 1. 停止服务（更安全）
sudo systemctl stop rstudio-server
```

---

### 🗑️ 2. 清理 RStudio 用户缓存（安全，不会删代码和包）

这些目录存放的是你的会话状态、文件监控缓存、日志等，删除后 RStudio 会自动重建。

```bash
# 清理会话缓存（如果会话卡死，这招很管用）
rm -rf ~/.local/share/rstudio/sessions

# 清理文件监控缓存
rm -rf ~/.local/share/rstudio/monitored

# 清理 RStudio 日志（之前提过，这里再确认一下）
rm -rf ~/.local/share/rstudio/log/*

# 清理 RStudio 的全局缓存（如果有）
rm -rf ~/.cache/rstudio
```

> **说明**：`~/.local/share/rstudio/` 下可能还有一个 `history_database` 文件（记录你输入过的命令历史），如果你也想清空命令历史，可以执行 `rm -f ~/.local/share/rstudio/history_database`。**这不会影响你的代码文件。**

---

### 🧹 3. 清理 R 的临时文件与安装缓存

R 在运行和安装包时会产生临时文件，这些文件通常在 `/tmp` 下，重启后本应自动清除，但有时会残留。

```bash
# 清理 R 的临时目录
rm -rf /tmp/Rtmp*

# 清理 R 包的下载缓存（如果存在）
rm -rf ~/.cache/R/install
rm -rf ~/.cache/R
```

> **注意**：`~/.cache/R` 一般只存放安装包时的临时压缩包，删除是安全的。**不要**删除 `~/R/x86_64-pc-linux-gnu-library/` 或 `/opt/R/4.6.2/lib/R/library`，那是你已安装的 R 包本体。

---

### 🔄 4. 重启服务并验证

```bash
sudo systemctl start rstudio-server
```

然后刷新浏览器（建议用无痕模式）重新登录。如果之前有 `jsonrpc` 连接错误，清理会话缓存后大概率会恢复正常。

### 💡 补充：RStudio Server 的系统级缓存（可选）

如果你是用 `apt` 安装的 RStudio Server，它的程序文件在 `/usr/lib/rstudio-server/`，配置在 `/etc/rstudio/`。这些**不建议手动清理**，因为它们是程序本体。如果你确实想彻底重装 RStudio Server，可以：

```bash
# 卸载 RStudio Server（保留配置）
sudo apt remove rstudio-server

# 彻底清除（包括配置）
sudo apt purge rstudio-server

# 清理残留依赖
sudo apt autoremove
```

但通常没必要，日常清理上面第 2、3 步的用户缓存就足够了。

### 🚨 重要提醒：WSL2 磁盘空间释放

清理完这些文件后，你在 Ubuntu 里用 `df -h` 会看到空间释放了，但 **Windows 的 C 盘并不会立刻变大**。必须回到 Windows PowerShell 执行 `wsl --shutdown`，然后用 `diskpart` 的 `compact vdisk` 命令压缩虚拟磁盘，才能真正把空间还给 C 盘（具体命令见上一条回复）。
