以下操作手册基于你最终确定的 **Windows Server 2022 (21H2)** 路线重新整理。与早前 2025 方案的核心区别在于：系统版本回退到对 2018 年浪潮服务器兼容性更稳妥的 21H2，但 **WSL2 的安装从“手动启用组件”简化为一条命令**，后续 Ubuntu 内的计算环境配置逻辑基本不变。

---

## Tier 1：制作启动盘，安装 Windows Server 2022 (21H2)，启用 WSL2

### 1.1 安装前的关键准备：浪潮 2018 服务器的两个“关卡”

**第一关：确认 RAID 卡驱动**。2018 年浪潮服务器（如 NF5270M4、NF5280M5）装 Windows 最常见的翻车场景是：安装程序走到“选择磁盘”界面时**一片空白**。这不是硬盘或阵列损坏，而是 Windows Server 2022 安装镜像里缺少该机型的 RAID 卡驱动。**在制作启动盘之前**，先去浪潮官网的服务支持页面，输入服务器的序列号或具体型号，下载它在 **Windows Server 2019 或 2022 下的 RAID 卡驱动**（通常是包含 `.inf` 文件的文件夹），拷入一个单独的小 U 盘备用。很多情况下 2019 的驱动在 2022 下可以通用。

**第二关：BIOS 中的 VT-x**。WSL2 依赖 CPU 硬件虚拟化，而这台 2018 年的服务器 **VT-x 很可能默认关闭，甚至选项被隐藏**。开机按 **F2** 或 **Del** 进入 BIOS（浪潮 NF 系列多数如此），在 `Advanced` → `Processor Configuration` 下找到 **Intel Virtualization Technology**，设为 `Enabled`。如果找不到这个选项，先把 `CPU Power Management` 中的 **C-State Control** 改为 `C1/C6 Only` 或 `Disabled`，VT-x 选项可能才会出现。同时确认 `Boot` 菜单中的启动模式（UEFI 或 Legacy），**Rufus 的参数必须与此一致**。

### 1.2 制作 Rufus 启动盘

准备 Windows Server 2022 ISO 和一个 ≥16 GB 的 U 盘。Rufus 中选中 U 盘，“引导类型选择”加载 ISO。**分区类型和目标系统跟随 1.1 中确认的 BIOS 启动模式**：UEFI 则选 **GPT + UEFI（非 CSM）** ；Legacy 则选 **MBR + BIOS**。点击“开始”写入。

### 1.3 安装系统：只格式化 C 盘，绝对不碰 D/E

从 U 盘启动（开机连按 **F11** 进入临时启动菜单，选择 U 盘设备最省事）。进入安装界面后选择 **Windows Server 2022 Standard（桌面体验）** ，不要选 Server Core，因为你需要运行 Office、Adobe、向日葵等图形软件。

到达“你想执行哪种类型的安装？”时，**必须选择“自定义：仅安装 Windows（高级）”** ，不要选“升级”。

进入分区列表后，**逐项核对“总大小”和“可用空间”** ，确认哪一个是原来的 C 盘（约 500 GB 固态），哪几个是 D/E 盘（机械 5T RAID 数据分区）。**只选中 C 盘分区及其所在磁盘的 EFI/MSR/恢复分区，点击“格式化”** 。对 D/E 分区**绝对不要点击“删除”“格式化”或“新建”** 。如果磁盘列表为空，点击“加载驱动程序”，浏览到 1.1 中准备的 RAID 驱动文件夹，注入后磁盘才会出现。选中 C 盘后点击“下一步”开始安装。

### 1.4 首次进入系统：检查盘符与补齐驱动

安装完成后设置 Administrator 密码登录。打开“磁盘管理”（`diskmgmt.msc`），检查 D/E 盘是否正常显示。如果盘符发生了变化，右键该卷 → “更改驱动器号和路径”改回原盘符。**在安装任何大型软件之前**，先打开**设备管理器**，检查是否有“未知设备”（通常是板载网卡、芯片组或管理芯片）。如有，使用浪潮官网下载的对应 Windows Server 2022 驱动补齐。这一步不做，后续网络配置和远程管理可能出现异常。

### 1.5 启用 WSL2 并安装 Ubuntu 24.04

Windows Server 2022 支持 **一条命令完成 WSL2 安装**。以**管理员身份**打开 PowerShell：

```powershell
wsl --install -d Ubuntu-24.04
```

这条命令会自动启用所需的可选组件（`Microsoft-Windows-Subsystem-Linux` 和 `VirtualMachinePlatform`）、下载最新 Linux 内核、将 WSL 2 设为默认，并安装 Ubuntu 24.04。执行完毕后**重启服务器**。

重启后 Ubuntu 会自动启动，提示创建 Linux 用户名和密码。**这个用户名和密码后续将用于 `sudo` 和 RStudio Server 登录，务必记住**。创建完成后，在 PowerShell 中执行 `wsl -l -v`，确认 Ubuntu 的 **VERSION 显示为 2**。如果显示为 1，执行 `wsl --set-version Ubuntu-24.04 2` 转换。

## Tier 2：Windows 宿主侧的软件安装

**原则**：Windows 侧主要用于图形化办公、远程管理和与同事协作；**真正的重计算任务全部放在 Tier 3 的 WSL2 Ubuntu 中完成**。两边的 Python/R 环境不要混用。

### 2.1 基础与远程工具

| 软件 | 安装要点 |
|---|---|
| **Git for Windows** | 官网下载 64 位安装包，默认选项。安装后在 PowerShell 中 `git --version` 验证。 |
| **VS Code（Windows 版）** | 下载 **System Installer**，安装时勾选“添加到 PATH”。装完后在 VS Code 扩展市场中安装 **WSL 扩展**，这是后续连接 Ubuntu 计算环境的主要入口。 |
| **向日葵（awesun）** | 官网下载 Windows 版正常安装，用于无图形显卡服务器的远程图形化管理。 |

### 2.2 Office 2021 与 Adobe 系列

**Office 2021**：建议使用 **Office LTSC 2021 批量版**，零售“家庭和学生版”在 Server 系统上的支持不确定性更高。**Adobe Acrobat / Illustrator**：正常安装 Windows 版本。需要注意的是，Adobe 产品在 Server 系统上并非官方主推平台，若安装器校验系统版本被拦截，优先尝试官方最新版本；如仍不行，需评估是否将图形工作放到普通客户端上完成。

### 2.3 Cytoscape 与 Watt Toolkit

**Cytoscape 3.10.4**：安装前确认已安装 **Java 11 或 17**（按其发布说明选择），然后运行 Cytoscape Windows 安装包。安装后至少启动一次，确认界面能正常打开。**Watt Toolkit** 按官网说明安装即可。

### 2.4 Windows 侧的 Anaconda、R、RStudio（轻量用途）

在 Windows 侧安装 **Anaconda** 和 **R + RStudio Desktop**，仅用于日常数据查看、简单图表和协作演示。**不要在这些环境中堆积计算包**；所有 conda 计算环境都建在 Tier 3 的 Ubuntu 中。RStudio Desktop 从 Posit 官网下载免费开源版，安装后会自动检测已安装的 R。

## Tier 3：WSL2 Ubuntu 下的基础环境

### 3.1 系统初始化与编译依赖

在 PowerShell 中输入 `wsl` 进入 Ubuntu 终端。首先更新系统并安装后续编译 GROMACS 和 R 包所需的依赖：

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y build-essential cmake git wget curl pkg-config \
  libopenblas-dev libfftw3-dev liblapack-dev zlib1g-dev gdebi-core
```

### 3.2 Git 与 VS Code（WSL 侧工作流）

`git` 已随上述命令安装。**VS Code 不需要在 Ubuntu 内单独安装**：在 Windows 的 VS Code 中装好 WSL 扩展后，从左下角选择 “Connect to WSL”，或在 Ubuntu 终端中进入项目目录执行 `code .`，即可在 WSL 远程模式下打开 Ubuntu 中的文件。后续所有 Python/R 开发都建议以这种方式进行。

### 3.3 Miniconda

所有 Python 计算平台都将通过 conda 隔离，**不要用系统 Python 直接 pip 安装科研包**。在 Ubuntu 中安装 Miniconda：

```bash
wget https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh
bash Miniconda3-latest-Linux-x86_64.sh
source ~/.bashrc
conda --version
```

安装完成后，建议先配置 `conda-forge` 频道：

```bash
conda config --add channels conda-forge
conda config --set channel_priority strict
```

### 3.4 R、RStudio Server 与 RTools 的 Linux 对应物

**R 与编译工具链**：

```bash
sudo apt install -y r-base r-base-core r-recommended r-base-dev
```

在 Ubuntu 下，**RTools 的角色由 `r-base-dev` + `build-essential` 承担**，不需要也不应该安装 Windows 版 RTools。`r-base-dev` 已经提供 `gcc`、`g++`、`gfortran` 和开发头文件，安装源码 R 包时足够使用。

**RStudio Server**：

```bash
wget https://rstudio.org/download/latest/stable/server/bionic/rstudio-server-latest-amd64.deb
sudo gdebi rstudio-server-latest-amd64.deb
sudo rstudio-server start
```

安装后 RStudio Server 监听 **8787** 端口。在 Windows 浏览器中访问 **`http://localhost:8787`**，用 1.5 中创建的 **Linux 用户名和密码**登录（不是 Windows 密码）。注意：**WSL 重启后 RStudio Server 不会自动启动**，需要重新执行 `sudo rstudio-server start`。

### 3.5 smina（分子对接，为 Tier 4 的 CADD 做准备）

smina 是 CPU 密集型的命令行对接工具，在 WSL2 Ubuntu 中通过 conda-forge 安装：

```bash
conda create -n docking python=3.10 -y
conda activate docking
conda install -y smina
smina --help
```

**关键实践**：smina 批量对接时的主要瓶颈之一是配体文件的读写。**项目文件务必放在 Ubuntu 内部文件系统（如 `~/projects`）中**，不要放在 `/mnt/c` 或 `/mnt/d` 下，否则跨文件系统 I/O 会严重拖慢筛选速度。

### 3.6 GROMACS（CPU-only，从源码编译）

**不要用 `apt install gromacs` 作为生产环境**，发行版包通常未针对你的 CPU 指令集优化。从源码编译一个明确禁用 GPU 的 CPU-only 版本。

先确认 CMake 版本 ≥ 3.28：

```bash
cmake --version
```

如版本不足，可通过 Miniconda 安装新版 CMake：

```bash
conda install -n base -y cmake
```

然后编译 GROMACS（以 2025.3 为例）：

```bash
mkdir -p ~/src && cd ~/src
wget https://ftp.gromacs.org/gromacs/gromacs-2025.3.tar.gz
tar xzf gromacs-2025.3.tar.gz
cd gromacs-2025.3
mkdir build && cd build
cmake .. \
  -DCMAKE_INSTALL_PREFIX=$HOME/opt/gromacs-2025.3 \
  -DGMX_GPU=OFF \
  -DGMX_MPI=OFF \
  -DGMX_OPENMP=ON \
  -DGMX_BUILD_OWN_FFTW=ON \
  -DREGRESSIONTEST_DOWNLOAD=ON
make -j$(nproc)
make check
make install
```

关键参数说明：`-DGMX_GPU=OFF` 明确关闭 GPU（你的服务器无 GPU）；`-DGMX_OPENMP=ON` 启用多核 CPU 并行；`-DGMX_BUILD_OWN_FFTW=ON` 让 GROMACS 自建 FFTW，避免系统库版本冲突。`make check` 建议执行，确认编译产物正确。

安装完成后，将 GROMACS 加入 PATH：

```bash
echo 'source $HOME/opt/gromacs-2025.3/bin/GMXRC' >> ~/.bashrc
source ~/.bashrc
gmx --version
```

CPU-only 的 GROMACS 在 WSL2 中与原生 Linux 性能基本持平，可以放心用于生产模拟。

## Tier 4：WSL2 下的计算平台环境

每个平台一个**独立 conda 环境**，互不干扰。R 侧不使用 conda 隔离也可以，RStudio Server 为单用户单会话，但建议按项目使用 `renv` 管理包版本。

### 4.1 Python 环境一：可解释机器学习（XAI）

```bash
conda create -n xai python=3.11 -y
conda activate xai
conda install -y numpy pandas scikit-learn matplotlib seaborn jupyter ipykernel
pip install shap lime
```

可选安装树模型库：`conda install -y xgboost lightgbm`。验证：`python -c "import shap, lime, sklearn; print('XAI OK')"`。在 VS Code 或 Jupyter 中使用时，将该环境注册为 kernel，即可直接在 WSL 远程会话中运行 Notebook。

### 4.2 Python 环境二：CADD / 药物设计

CADD 没有单一“平台”能覆盖全部需求，以下组合均 **CPU-only 可运行**。

**TeachOpenCADD（教学与基础工作流，推荐首先安装）** ：

```bash
conda create -n cadd python=3.10 -y
conda activate cadd
conda install -y teachopencadd
teachopencadd -h
```

TeachOpenCADD 通过 conda 包安装后，运行 `teachopencadd start .` 即可在当前目录创建工作区，用 Jupyter Lab 打开其中的 talktorial 材料。它提供了基于开源化学信息学工具的完整 CADD 流程示例，适合在 CPU 上逐步跑通。

**smina 对接环境**（已在 3.5 创建）保留为专门执行对接的环境。典型流程：在 `cadd` 环境中做数据准备和结果整理，在 `docking` 环境中运行 `smina` 批量对接，结果再回到 `cadd` 或 R 中分析。

**需要避开的工具**：基于 FEP 的 CADD 工具（如部分 Alchemd-toolkit 组件）明确要求 NVIDIA GPU + CUDA，你的无 GPU 服务器不适合部署这类组件。选型时优先确认“CPU-only 可运行”。

### 4.3 Python 环境三：光谱数据分析

基础光谱处理依赖 `numpy`、`scipy`、`pandas`、`matplotlib`、`scikit-learn`，专用包可按你的光谱类型选择。

```bash
conda create -n spectra python=3.11 -y
conda activate spectra
conda install -y numpy scipy pandas matplotlib scikit-learn jupyter ipykernel
```

**按光谱类型选装专用包**（任选或按需组合）：

- **化学光谱（红外、拉曼、近红外等）** ：`conda install -y spectrochempy`。SpectroChemPy 是专门用于化学光谱数据处理、分析和建模的框架，支持 Linux 平台。
- **通用光谱预处理**：`conda install -y spectrapepper`，提供简化的光谱数据预处理工具。
- **天文/特定波段光谱**：`conda create -n pyspextool python=3.13 -y && conda activate pyspextool && pip install pyspextool`（按其文档建议在 conda 环境中使用）。

验证：`python -c "import spectrochempy; print('spectra OK')"`（如果安装了 SpectroChemPy）。

### 4.4 R 平台：网络药理学与生物信息学

基础 R 已在 3.4 中安装。在 R 控制台或 RStudio Server 中操作。

**安装 BiocManager**：

```r
install.packages("BiocManager")
```

**网络药理学**：`drugfindR` 用于基于 LINCS 等资源的药物–基因关联分析。推荐从 Bioconductor 安装：

```r
BiocManager::install("drugfindR")
```

如果当前 Bioconductor 稳定版尚未包含该包，可使用 devel 频道：

```r
BiocManager::install("drugfindR", version = "devel")
```

需要注意 **Bioconductor 版本与 R 版本绑定**，保持 R 和 BiocManager 的版本匹配，不要跨版本盲目安装。

**生物信息学常用基础包**：按需安装 `AnnotationDbi`、`clusterProfiler`、`org.Hs.eg.db`、`DESeq2`、`limma` 等。同样通过 `BiocManager::install(...)` 安装。

**网络分析与可视化**：在 R 中安装 `igraph`、`ggraph` 用于网络拓扑分析和静态图绘制；**Cytoscape** 仍在 Windows 侧承担交互式网络图的美化和布局。

## 无 GPU 多核服务器的关键提醒

**D/E 盘安全是第一优先级**。安装系统时宁可多花时间逐项核对分区大小，也不要凭分区顺序判断。建议在动手前将 D/E 上最关键的数据额外复制一份到移动硬盘或网络存储，作为分区操作之外的最后兜底。

**所有计算项目放在 Ubuntu 内部文件系统**（`~/projects` 等），不要放在 `/mnt/c`、`/mnt/d`。跨文件系统 I/O 会显著拖慢 smina 批量筛选和 GROMACS 轨迹读写。

**GROMACS 坚持 `-DGMX_GPU=OFF` 源码编译**，不要用 Windows 版 GROMACS，也不要用 `apt` 的通用包。编译一次，后续可直接使用。

**RStudio Server 的启动是手动的**。WSL 重启后需要 `sudo rstudio-server start`，这不是故障，是 WSL 下 systemd 管理方式的正常表现。

**每个 Python 平台独立 conda 环境**。XAI、CADD、光谱分析对 Python 版本和依赖包的要求可能差异很大，共用 base 环境会在后续安装新包时引发难以排查的依赖冲突。

## 内存问题

96 GB 内存只显示 64 GB，这个差值很典型，问题大概率出在**BIOS 设置或物理安装**层面，而不是 Windows Server 2022 本身（Standard 版支持的内存远超 96 GB）。建议你按 **“先看 BIOS，再查物理，最后查系统”** 的顺序来定位。

### 🔍 第一步：先去 BIOS 里看一眼，这是最关键的分岔路口

浪潮官方手册给出的排查逻辑非常明确：**进 BIOS setup 查看内存容量**。

重启服务器，按 **F2** 或 **Del** 进入 BIOS，找到 **System Information** 或 **Memory Information** 之类的页面。

- **如果 BIOS 里也只显示 64 GB**：问题在硬件或 BIOS 固件层面，Windows 本身是无辜的。直接跳到第二步。
- **如果 BIOS 里能完整识别 96 GB**：问题在 Windows 层面，跳到第三步。

### 🛠️ 第二步（BIOS 只认 64 GB）：两个浪潮特有的 BIOS 选项

根据浪潮服务器的已知案例，64 GB 这个“坎”常常和以下两个 BIOS 选项直接相关。

**① 优先检查：`Enforce POR`（强制 POR 策略）**

有明确的案例记录：浪潮服务器升级内存后**仅识别 64 GB**，更换内存条无效，最终通过**禁用 `Enforce POR`** 解决。`Enforce POR` 默认开启时，会强制内存按照旧版规范运行，可能限制大容量内存条的完整识别。

**操作路径**（不同型号菜单名可能略有差异，供参考）：
`Socket Configuration` → `Memory Configuration` → 找到 **`Enforce POR`**，将其设为 **`Disabled`**，保存重启。

**② 备选检查：内存重映射（Memory Remap / Above 4G Decoding）**

部分内存容量可能被 PCIe 设备等硬件占用的地址空间“遮蔽”了。在 BIOS 中寻找 **`Memory Remap Feature`**、**`Above 4G Decoding`** 或类似名称的选项，确保其处于 **`Enabled`** 状态。这个选项在服务器 BIOS 中不一定叫同一个名字，可以在 `Advanced` 或 `Chipset` 菜单下留意。

### 🔌 第三步（BIOS 只认 64 GB）：排查物理安装

如果 BIOS 设置调整后依然无效，需要检查内存条本身。

- **插槽顺序是否正确**：服务器内存有严格的安装优先级。通常需要**优先插满 CPU0 对应的插槽**（如 A1/B1/C1...），再扩展到 CPU1 的插槽。跨 CPU 或跳着乱插，可能导致部分内存无法被识别。96 GB 的配置（比如 3 条 32 GB？或者 6 条 16 GB？）如果插槽分布不合理，出现 64 GB 的识别结果并不意外。建议查阅你这台浪潮机型的具体内存安装顺序表。
- **是否存在内存混插**：服务器通常**不支持不同类型（如 RDIMM 与 LRDIMM）、不同容量或不同频率的内存混插**。如果 96 GB 是由不同批次或规格的内存条拼凑的，部分内存可能被 BIOS 直接忽略。可以尝试**只保留能组成 64 GB 的那部分内存条**，逐一替换测试，定位是哪一条或哪几条不被识别。
- **基础物理检查**：断电后，重新拔插所有内存条，确保卡扣完全闭合。如果条件允许，可以清洁一下金手指。

### 💻 第四步（BIOS 认 96 GB，但 Windows 只显示 64 GB）：系统层排查

如果 BIOS 里是完整的 96 GB，进入 Windows 后只剩 64 GB，检查以下几点：

1. **`msconfig` 的内存限制**：按 `Win + R` 输入 `msconfig`，进入 **“引导”** 选项卡 → **“高级选项”** ，确认 **“最大内存”** 复选框**没有被勾选**。如果被勾选了，取消它并重启。
2. **查看“为硬件保留的内存”**：打开任务管理器 → 性能 → 内存，看“为硬件保留”一项的数值。如果保留量异常大（比如接近 32 GB），说明 Windows 虽然看到了硬件，但无法使用这部分地址空间。这与 BIOS 的内存映射设置有关，需要回到第二步检查 `Memory Remap` / `Above 4G Decoding`。
3. **系统版本限制**：虽然 Windows Server 2022 Standard 支持远超 96 GB 的内存，但如果你安装的是某些特定的**评估版、未激活版本或早期构建**，理论上可能存在异常限制。确保系统已通过 Windows Update 更新到较新的累积补丁水平。

### 💎 给你的操作优先级建议

你的情况是 96 GB 变成 64 GB，差值正好是 32 GB，**`Enforce POR` 被启用**和**内存插槽顺序不符合规范**是两个最值得优先验证的方向。建议你：

**重启进 BIOS → 先看 BIOS 识别的总容量 → 如果只认 64 GB，优先尝试禁用 `Enforce POR` → 无效则核对内存插槽顺序并排查混插 → 最后再回头检查 Windows 侧的 `msconfig` 和硬件保留设置。** 如果以上步骤均无效，浪潮官方手册的建议是联系浪潮客服，并提供主机序列号和详细故障信息。

## conda的镜像和jupyter配置

以下是针对 Conda、Pip 中科大镜像，以及 JupyterLab 启动配置的完整补充，可以直接追加到你现有的 yml 和操作流程中。

---

### ⚙️ Conda 中科大镜像配置（推荐直接覆盖 `.condarc`）

最稳妥的方式是**直接手动覆盖配置文件**，而不是用 `conda config --add` 逐条添加。因为 `--add` 只会在原有基础上叠加，海外 `defaults` 源可能残留，导致依赖解析时混用国内与国外源，引发 `UnsatisfiableError` 或安装卡死。

**操作步骤**：

1. **先查看当前配置来源**，确认是否有旧源残留：
   ```bash
   conda config --show-sources
   ```

2. **直接编辑 `~/.condarc`**（Linux 路径），内容写成“**no defaults**”模式：
   ```yaml
   channels:
     - https://mirrors.ustc.edu.cn/anaconda/pkgs/main/
     - https://mirrors.ustc.edu.cn/anaconda/pkgs/r/
     - https://mirrors.ustc.edu.cn/anaconda/pkgs/msys2/
     - https://mirrors.ustc.edu.cn/anaconda/cloud/conda-forge/
     - https://mirrors.ustc.edu.cn/anaconda/cloud/bioconda/
   show_channel_urls: true
   ```
   **关键点**：`main` 放在最上面（核心 Python 包所在）；**不要保留任何 `- defaults` 行**，哪怕只有一行也不行；**不要加 `pkgs/free`**，该频道在 Conda 4.7+ 已废弃，加了反而容易报错。

3. **清理索引缓存并验证**：
   ```bash
   conda clean -i
   conda search numpy --info
   ```
   输出中每个版本的下载 URL 应**全部以 `https://mirrors.ustc.edu.cn/` 开头**，才算真正生效。如果仍出现 `anaconda.org`，说明 `.condarc` 里还有残留的 `defaults`。


### 📦 Pip 中科大镜像配置（`pip config set` 永久生效）

**永久配置命令**（推荐，自动写入用户级配置）：

```bash
pip config set global.index-url https://pypi.mirrors.ustc.edu.cn/simple/
pip config set global.trusted-host pypi.mirrors.ustc.edu.cn
```

**验证**：

```bash
pip config list
```
输出中应包含这两行，之后所有 `pip install` 会自动走中科大镜像。

**临时指定**（单次安装，不改配置）：

```bash
pip install <package> -i https://pypi.mirrors.ustc.edu.cn/simple/
```

**注意 URL 末尾的 `/simple/`**，少了斜杠会返回 404。中科大 PyPI 镜像对大型包（如 PyTorch）的同步可能略有延迟，遇到安装失败可临时切回清华源试一次。


### 🚀 JupyterLab 启动配置

你已经有专用的 `jupyter` 环境（含 `jupyterlab` + `nb_conda_kernels`）。日常启动方式有两种：**命令行参数**和**持久化配置文件**。

#### 方式一：命令行直接启动（最常用）

```bash
conda activate jupyter
jupyter lab --no-browser --ip=0.0.0.0 --port=8888 --notebook-dir=~/projects
```

- `--no-browser`：不尝试自动打开浏览器（WSL2 环境下通常没有图形浏览器）。
- `--ip=0.0.0.0`：允许来自 Windows 宿主机的访问。WSL2 的 localhost 转发会自动把 `localhost:8888` 映射到 Ubuntu 内的 8888 端口。
- `--port=8888`：指定端口，如果 8888 被占用，可换成 `8889` 等。
- `--notebook-dir=~/projects`：设置文件浏览器的根目录，避免看到整个 `/home`。

**从 Windows 浏览器访问**：`http://localhost:8888`。首次启动时终端会输出一个带 token 的完整 URL，复制那个 URL 打开即可。

#### 方式二：持久化配置文件（一次配置，长期生效）

生成默认配置文件：

```bash
conda activate jupyter
jupyter lab --generate-config
```

编辑 `~/.jupyter/jupyter_lab_config.py`（路径通常在 `~/.jupyter/` 下），取消注释并修改以下常用项：

```python
c.ServerApp.ip = '0.0.0.0'
c.ServerApp.open_browser = False
c.ServerApp.port = 8888
c.ServerApp.root_dir = '/home/<你的用户名>/projects'
c.ServerApp.allow_remote_access = True
c.ServerApp.iopub_data_rate_limit = 100000000000
```

- `root_dir` 是文件浏览器的根目录，建议设为你的项目目录（如 `~/projects`）。
- `allow_remote_access = True` 配合 `ip = '0.0.0.0'` 实现 WSL2 宿主机访问。
- `iopub_data_rate_limit` 可避免输出大量数据（如光谱矩阵、图像）时前端被限流。

配置好后，以后只需：

```bash
conda activate jupyter && jupyter lab
```


### ⚠️ 与多环境内核的配合提醒

你之前配置的 `nb_conda_kernels` 依赖 JupyterLab 启动时对 conda 环境的自动扫描。**镜像配置本身不影响内核发现逻辑**，但注意两点：

**第一**，每个计算环境（`spectra-core`、`libs`、`eem` 等）里安装的 `ipykernel` 是通过 pip 安装的。pip 镜像只影响包的下载来源，不会改变内核注册行为。

**第二**，如果你在 `jupyter` 环境里也配置了 pip 镜像，那么 `nb_conda_kernels` 后续升级时也会走中科大源，与 yml 重建流程一致，不会引入不一致的依赖来源。

**验证整条链路**：启动 JupyterLab 后，新建 Notebook，Kernel 下拉菜单中应能看到 `Python [spectra-core]`、`Python [libs]` 等条目。如果某个环境没出现，回到该环境确认 `ipykernel` 已安装（`conda list ipykernel` 或 `pip show ipykernel`），然后重启 JupyterLab 内核列表刷新。
