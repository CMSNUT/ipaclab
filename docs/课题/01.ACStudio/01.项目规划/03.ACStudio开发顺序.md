下面是 ACStudio 的开发顺序。核心原则是**垂直切片先行、依赖倒置**：每一步都产出可运行的东西，而不是先把某一层全部做完再做下一层。计算核心、UI 骨架、数据层三者的推进节奏要交错，避免“计算全做完但 UI 跑不起来”或“UI 全搭完但没数据可显示”。

---

## 总体节奏

```
第0步  工具链与预置包生成器
第1步  ac_core 垂直切片（Titra 酸碱滴定）
第2步  UI 骨架 + 垂直切片联调（假数据）
第3步  数据层 + 预置包解锁 + 登录闭环
第4步  化学分析模块补全（Grav、Prep）
第5步  仪器分析交互原型验证
第6步  仪器分析模块补全（UVVis、FLS、Atom、Chroma）
第7步  巩固与拓展标签页
第8步  Electro + 全局工具
第9步  授权与加密接入
第10步 三平台 CI 与发布
第11步 在线维护预留（文档与接口，不实现）
```

第9步之前全部在开发机上以 Python 脚本运行，**不碰 PyArmor / Nuitka**。打包永远放在最后，因为它会把调试周期拉长一个量级。

---

## 第0步：工具链与预置包生成器（约 3—5 天）

**为什么先做这个**：登录、权限、用户面板都依赖预置数据包，而预置包生成器是你作为发行方的离线工具，不是软件运行时的一部分。先把“怎么造数据”跑通，后面数据层才有东西可读。

**产出**：

- 仓库目录按架构文档建好，`pyproject.toml` 与依赖锁定。
- `tools/build_data_pack.py`：读入一个手工准备的 SQLite（先放 5 个假学生），输出 `users.enc` / `users.sig` / `manifest.json`。
- `tools/hash_passwords.py`：argon2 批量哈希。
- `data/schema.sql`：静态表与动态表建表脚本，含 `sync_state` 等预留字段。
- `ac_auth/data_pack.py` 的**解锁函数**（先只做 AES 解密 + 版本比对，Ed25519 验签可延后到第9步，但接口签名先定好）。
- 单元测试：生成包 → 解密 → 读出的学生数一致。

**交付判据**：一条命令能生成预置包，另一条命令能解密并读出学生列表。

---

## 第1步：ac_core 垂直切片——Titra 酸碱滴定（约 1 周）

**产出**：

- `ac_core/chemical/titration.py` 的酸碱滴定函数：滴定曲线、分布分数、计量点、突跃范围。
- `ac_core/models/titration_models.py`：输入输出 dataclass。
- `tests/test_core_titration.py`：与教材典型体系比对数值。

**关键验证**：`pHcalc` 在多元酸、不同浓度下的求解是否稳定；精确解与教材近似公式的差异是否在可接受范围（这个差异后面要作为“查看计算过程”的教学内容）。

**交付判据**：纯 Python 跑出与教材一致的滴定曲线数据，测试全绿。

---

## 第2步：UI 骨架 + 垂直切片联调（约 1—1.5 周）

**产出**：

- `main_window.py`：菜单栏、状态栏、三栏布局（左导航、中工作区、右用户面板占位）。
- `navigation/sidebar.py`：化学分析 / 仪器分析两个分区的导航项（先只有 Titra 可点，其余置灰）。
- `widgets/plotly_view.py`：`QWebEngineView` 封装 Plotly 图。
- `modules/titra/learn_tab.py`：三个滑块 + 滴定曲线 + 计量点/突跃范围数值输出。
- 用户面板先显示**硬编码的假用户**和真实的北京时间。

**关键验证**：拖动滑块时 Plotly 图在 `QWebEngineView` 中的更新延迟是否可接受；高 DPI 下的字体与布局。

**交付判据**：Windows 上双击运行 `python main.py`，能进入主界面，Titra 学习页滑块联动曲线。

---

## 第3步：数据层 + 预置包解锁 + 登录闭环（约 1.5—2 周）

**这是第一个真正的里程碑**：产品从“演示”变成“有真实用户”。

**产出**：

- `data_manager/db/connection.py`：SQLite 连接、用户目录定位（三平台路径）、迁移机制。
- `data_manager/repositories/base.py` + `local_user.py` + `local_progress.py`。
- `services/auth_service.py`：登录、会话、权限检查。
- `ac_auth/data_pack.py` 完整接入：启动时验签（此时可先用简化验签）→ 解密 → 覆盖静态表、保留动态表与已改密码。
- `ac_ui/dialogs/login_dialog.py`：账号密码登录。
- `ac_ui/user_panel/panel.py` + `clock.py`：头像、学号、姓名、班级、北京时间、星期、退出。
- 登录后 Titra 模块才可进入（权限检查的最小实现）。

**关键验证**：预置包更新后，学生密码不被重置；本地库被手工改 `role` 时登录被拒绝。

**交付判据**：真实预置包 → 登录 → 显示真实身份信息 → 进入 Titra。

---

## 第4步：化学分析模块补全——Grav、Prep（约 1—1.5 周）

**产出**：

- `ac_core/chemical/gravimetry.py` + `preparation.py`（`efta` 集成 + 简化 SPE 模型）。
- `modules/grav/` 与 `modules/prep/` 的三标签骨架（学习页完整，巩固/拓展先占位）。
- 每个模块的引导性任务卡。
- 学习进度写入 `learning_progress` 表。

**交付判据**：三个化学分析模块的学习页全部可用，进度可记录。

---

## 第5步：仪器分析交互原型验证（约 1 周）

**这一步单独拎出来，因为它是整个项目最大的技术风险**。在批量做仪器分析模块之前，先做两个最小原型：

- **色谱峰手动选点积分**：Plotly `selectedpoints` / `lasso` 在 `QWebEngineView` 中是否流畅；选点后能否实时算出峰面积。
- **FLS 双波长扫描**：两个滑块（激发波长、发射波长）+ 两条曲线联动，切换“扫激发/扫发射”模式。

**如果原型不通过**，就在这一步决定改用 Matplotlib Qt 后端或自定义 Qt 绘图，而不是等六个模块做完再返工。

**交付判据**：两个原型在目标机器上操作流畅，交互方案确定。

---

## 第6步：仪器分析模块补全（约 2—2.5 周）

**顺序**：`UVVis` → `FLS` → `Atom` → `Chroma`。先做 UVVis 是因为它最简单、且 `spectra_common.py` 的峰形模拟与拟合函数在这里第一次成型，后面三个模块复用。

**产出**：

- `ac_core/instrumental/spectra_common.py`：峰形模拟、标准曲线拟合共用。
- `uvvis.py` / `fls.py` / `atom.py` / `chroma.py` 及对应 models。
- 四个模块的学习页（学习页完整，巩固/拓展先占位）。
- `Prep` 与 `UVVis` 的衔接任务卡（“先富集再测定 vs 直接测定”）。

**交付判据**：七个模块（含第4步三个）学习页可用；光谱与色谱的图形交互达到第5步原型的流畅度。

---

## 第7步：巩固与拓展标签页（约 1.5—2 周）

**产出**：

- `services/quiz_service.py`：题库加载、判分、错题本。
- `services/report_service.py` + `report_editor.py`：报告模板、格式校验。
- 每个模块的 `quiz_tab.py` 与 `extend_tab.py` 填充内容。
- 题库数据格式（JSON 或 SQLite）与首批题目（每模块 10—15 题，含选择/填空/计算/解答/设计）。
- `experiment_records` 与 `reports` 表写入。

**关键设计**：题库与报告模板是**内容**不是**代码**，应做成可独立更新的数据文件，方便教师后续增补而不重新打包。

**交付判据**：任选一个模块，完成“学习 → 巩固答题 → 错题收录 → 拓展设计 → 生成报告”全流程。

---

## 第8步：Electro + 全局工具（约 1 周）

**产出**：

- `ac_core/instrumental/electro.py` + 模块学习页。
- `global_tools/`：科学计算器、常数/周期表速查、单位换算、截图与 PDF 导出。
- 明/暗主题切换、演示模式（全屏、隐藏侧边栏、放大字体）。

**交付判据**：八个模块全部可用；课堂投影场景下演示模式正常。

---

## 第9步：授权与加密接入（约 2 周）

**产出**：

- `ac_auth/license_verify.py`：Ed25519 验签、机器码比对、到期检查。
- `ac_auth/clock_guard.py`：本地时钟回拨检测。
- `ac_auth/machine_id.py`：三平台机器码。
- 预置包解锁升级为完整 Ed25519 验签（第3步的简化版替换掉）。
- `tools/sign_license.py`：签发 `.lic`。
- `main.py` 入口顺序固定为 `guard → data_manager.init → ac_ui.launch`。
- PyArmor 加密 `ac_core` 与 `ac_auth`，验证加密后计算与授权正常。

**关键验证**：无 `.lic` 拒绝进入；过期 `.lic` 拒绝进入；改系统时间触发回拨警告；预置包被篡改时验签失败。

**交付判据**：授权全链路可验证，加密产物功能与未加密一致。

---

## 第10步：三平台 CI 与发布（约 2 周）

**产出**：

- GitHub Actions 矩阵：三平台并行 `测试 → PyArmor（指定平台）→ Nuitka → 冒烟测试 → 上传产物`。
- `ac_build/ci/smoke_test.py`：启动 → 授权 → 登录 → 进入至少两个模块 → 退出。
- 产物形态：Windows `.exe`；Linux `.bin` 或 AppImage；macOS `.app` → `.dmg`。
- macOS 签名与公证（如有 Apple Developer 账号）。
- 发布页：版本号、哈希值、更新日志、第三方开源许可声明。

**顺序建议**：先让 Windows 产物稳定，再合并 macOS 构建分支，最后 Linux。不要三平台同时调 CI。

**交付判据**：三平台产物均可完成冒烟测试。

---

## 第11步：在线维护预留（文档级，约 2—3 天）

**产出**：

- `data_manager/sync/sync_service.py` 与 `conflict.py` 保留骨架与契约注释。
- `config.json` 的 `server` 段默认关闭。
- 一份内部文档说明启用在线维护时的改动点（替换仓储实现、开启 `mode=hybrid`、实现三个 API）。

**不做的事**：不写真实网络请求、不建服务器、不做教师端界面。这一步只是把“未来切换点”钉死在代码里。

---

## 并行与关键依赖

| 可并行 | 说明 |
|---|---|
| 第1步与第0步后半段 | 预置包工具与计算核心无依赖 |
| 第4步与第5步 | Grav/Prep 与仪器分析原型互不依赖 |
| 第6步内部 | UVVis 完成后，FLS/Atom/Chroma 可分工并行 |
| 第7步题库编写 | 可与第6步并行，题库是数据文件 |

**强依赖（不可颠倒）** ：

- 第2步依赖第1步的计算函数。
- 第3步依赖第0步的预置包生成器。
- 第6步依赖第5步的交互方案定论。
- 第9步依赖第3步的数据层与第8步的完整功能。
- 第10步依赖第9步的加密产物。

## 时间估算汇总

| 步骤 | 工期 | 累计 |
|---|---|---|
| 0 工具链与预置包生成器 | 3—5 天 | 0.5—0.7 周 |
| 1 Titra 计算核心 | 1 周 | 1.5—1.7 周 |
| 2 UI 骨架 + 联调 | 1—1.5 周 | 2.5—3.2 周 |
| 3 数据层 + 登录闭环 | 1.5—2 周 | 4—5.2 周 |
| 4 Grav + Prep | 1—1.5 周 | 5—6.7 周 |
| 5 仪器分析原型验证 | 1 周 | 6—7.7 周 |
| 6 仪器分析四模块 | 2—2.5 周 | 8—10.2 周 |
| 7 巩固与拓展 | 1.5—2 周 | 9.5—12.2 周 |
| 8 Electro + 全局工具 | 1 周 | 10.5—13.2 周 |
| 9 授权与加密 | 2 周 | 12.5—15.2 周 |

---

## 每个阶段结束时的固定动作

1. 跑全部单元测试与冒烟测试。
2. 在 Windows 上做一次手工回归（登录 → 目标模块 → 退出）。
3. 更新 `CHANGELOG.md`。
4. 打一个 git tag，保留可回退的基线。

**最容易被跳过、但最不该跳过的是第5步的原型验证**。仪器分析的图形交互是整个项目里唯一“做错了要大改”的地方，用一周时间先验证，比后面六个模块返工便宜得多。
